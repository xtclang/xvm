Ecstasy composition specialization:

1. Composition specialization refers to the ability for an Ecstasy type that declares one or more
   type parameters and is composed with one or more conditional incorporations to be specialized in
   terms of its composition based on a combination of (i) the types specified for those type
   parameters, and (ii) the set of conditional incorporations that occur based on those specified
   types. For example, the Range class implies two specializations: (0) when Element is NOT
   Sequential, and (1) when Element IS Sequential. For example, the ListMap class implies four
   specializations: (00) when Key is NOT immutable Hashable and Value is NOT Shareable, (01) when
   Key IS immutable Hashable and Value is NOT Shareable, (10) when when Key is NOT immutable
   Hashable but Key IS immutable Object and Value IS Shareable, and (11) when Key IS immutable
   Hashable and Value IS Shareable.

2. For the JIT project, Ecstasy composition specialization is the first step of specialization,
   referred to as "layer one specialization". This corresponds to the minimum set of TypeInfo
   objects that must be calculated for an instantiable class; for example, Range requires only 2
   TypeInfo objects to be calculated ("private Range<Orderable>" and "private Range<Sequential>"),
   and ListMap requires 4 TypeInfo objects to be calculated ("private ListMap<Object, Object>",
   "private ListMap<immutable Hashable, Object>",  "private ListMap<immutable Object, Shareable>",
   and "private ListMap<immutable Hashable, Shareable>"). Each type parameter in these examples is
   calculated as the intersection of the class' parameter constraint type (such as Orderable in the
   Range example) with each of the applied conditional incorporation parameter constraint types
   ("immutable Object" and "immutable Hashable" in the Listmap "11" case).

3. For each layer one specialization of Ecstasy types, the JIT will produce a "class of" ("c"
   prefix) classfile and an "interface of" ("i" prefix) classfile.

4. It is worth stating: the resulting set of layer one specialized compositions is enumerable at
   Ecstasy compile-time, and thus is also enumerable at JIT time.

Ecstasy to Java Classfile compiler (JIT) class naming conventions:

1. All Java interfaces produced by the JIT compiler extend "org.xtclang.ecstasy.Object"; all
   produced Java classes extend (directly or indirectly) "org.xtclang.ecstasy.nObject", which
   implements "org.xtclang.ecstasy.Object".

2. An Ecstasy type is a "Java-Primitive" type iff we choose to provide a second optimized
   representation of the type using a Java primitive value; for example: Int64 as long, Char as int,
   Boolean as boolean.

3. An Ecstasy type is an "XVM-Primitive" type iff we choose to implement it using two or more Java
   values (which at present are all of primitive Java types); for example Int128 as (long, long),
   Range<Int> as (long, long, boolean, boolean).

4. An Ecstasy type is a "JIT-Primitive" type iff it is a Java-Primitive type, an XVM-Primitive type,
   or the "Nullable" form of either.

5. For every Ecstasy type T there is a "JIT Call Class" CC(T), such that:
    a) the JIT Call Class indicates the Java name of the classfile;
    b) the JIT Call Class indicates whether the classfile is a Java interface or a Java class;
    c) for any Ecstasy method with a parameter or return of type T, the corresponding Java signature
       will use the Java class or interface name provided by CC(T);
    d) the "nObject.$xvmType()" method of the classfile specified by CC(T) will return a
       TypeConstant that will evaluate as "isA()" of the TypeConstant for type T;
    e) if CC(T) indicates a Java class, then instances of that Java classfile can be cast to
       "org.xtclang.ecstasy.nObject";
    f) all classfiles indicated by CC(T) can be cast to the "org.xtclang.ecstasy.Object" interface.

6. For every Ecstasy type T that represents an instantiatable class there is a "JIT Instance Class"
   IC(T), such that:
    a) the JIT Instance Class indicates the Java name of the instantiable classfile;
    b) a "NEW" op for type T produces an instance of Java class IC(T), or a subclass thereof;
    c) IC(T) and CC(T) are not neccessarily the same, in which case
        1) CC(T) is either an abstract Java class or an interface;
        2) IC(T) either extends or implements CC(T).
    d) if CC(T) is an abstract class, then JIT generates an equivalent interface by prefixing "i$"
       to the class name, which CC(T) naturally implements;
    e) if T contains a formal type, the IC(T) is not known at the compile time and will be computed
       at the run time instead.

7. For an Ecstasy type T that is an interface, mixin, annotation or a pure type, there is no IC(T)
   and only CC(T) is generated, which in that case is a Java interface. For an Ecstasy abstract
   class, there is no IC(T) and CC(T) is an abstract Java class.

8. An Ecstasy type is called "Specializable" iff:
    a) it is parameterized (has generic types);
    b) at least one of the generic type is constrained by a type that can be assigned from a
       JIT-Primitive type.

9. Java classes generated for a Specializable type fall into three categories:
   a) When at least one generic type parameter is a JIT-Primitive type, the corresponding produced
      Java class is called a "Specialized" class.
   b) If no generic type parameter is a JIT-Primitive type, the produced Java class is called a
      "Generalized" class.
   c) If the Specializable type is not an interface, then in addition to the "Generalized" and
      "Specialized" classes that the JIT may generate, it will:
      1) if the Specializable type does not extend a Specializable type then:
        i) generate an abstract Java class (Specialized Base Class [SBC]) that implements the
           Generalized interface and is extended by each of the "Generalized" and "Specialized"
           classes, and
        ii) generate a synthetic interface (Specialized base interface [SBI]) that contains all the
            methods of the SBC
      2) if the Specializable type extends a Specializable type, generate a "Generalized interface"
         that is implemented by all of the "Generalized" and "Specialized" classes and which
         implements SBI for the super class

   Note: Specializable Ecstasy types always have a single underlying class (as defined by the
         TypeConstant.isSingleUnderlyingClass() API)

   Example:
     If a Specializable Ecstasy type D<T1, T2, T3> extends a Specializable Ecstasy type B<T1, T2>
     and at least one of the generic types is JIT-Primitive then the corresponding Specialized Java
     class J(D<T1, T2, T3>) extends the Specialized Java class J(B<T1, T2>).
     If a Specializable Ecstasy type D<T1, T2, T3> extends a non-Specializable Ecstasy type
     B<T1, T2>, the Specialized Java class J(D<T1, T2, T3>) extends the Generalized J(D).

 - some A (might be Object, might be some abstract or non-abstract base class)
 - some B<T> : A    where B is for "Base" class
 - some D<T> : B<T> where D for "Derived" class

 JIT produces:
                         A (whatever it is)

                                 ^

                         interface i$B
class B<Object> -->      abstract B implements i$B     <--  class B<Int>      "the shoulders"

        ^                        ^                             ^
        |                        |                             |              "long arms"

class D<Object> ~~>      interface i$D extends i$B     <~~  class D<Int>
