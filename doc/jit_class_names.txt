I. Ecstasy composition specialization:

1. Composition specialization refers to the ability for an Ecstasy type that declares one or more
   type parameters and is composed with one or more conditional incorporations to be specialized in
   terms of its composition based on a combination of (i) the types specified for those type
   parameters, and (ii) the set of conditional incorporations that occur based on those specified
   types. For example, the Range class implies two specializations: (0) when Element is NOT
   Sequential, and (1) when Element IS Sequential. For example, the ListMap class implies four
   specializations: (00) when Key is NOT immutable Hashable and Value is NOT Shareable, (01) when
   Key is NOT immutable Hashable but Key IS immutable Object and Value IS Shareable, (10) when Key
   IS immutable Hashable and Value is NOT Shareable, and (11) when Key IS immutable Hashable and
   Value IS Shareable.

2. For the JIT project, Ecstasy composition specialization is the first step of specialization,
   referred to as "layer one specialization". This corresponds to the minimum set of TypeInfo
   objects (obviously a minimum of two, hence the term "specialization") that must be calculated for
   an instantiable class; for example, Range requires only two TypeInfo objects to be calculated
   ("private Range<Orderable>" and "private Range<Sequential>"), and ListMap requires four TypeInfo
   objects to be calculated ("private ListMap<Object, Object>", "private ListMap<immutable Hashable,
   Object>", "private ListMap<immutable Object, Shareable>", and "private ListMap<immutable
   Hashable, Shareable>"). Each type parameter in these examples is calculated as the intersection
   of the class' parameter constraint type (such as Orderable in the Range example) with each of the
   applied conditional incorporation parameter constraint types ("immutable Object" and "immutable
   Hashable" in the ListMap "11" case).

3. For each layer one specialization of Ecstasy types, the JIT will produce a "class of" ("c"
   prefix) classfile and an "interface of" ("i" prefix) classfile.

4. It is worth stating: the resulting set of layer one specialized compositions is enumerable at
   Ecstasy compile-time, and thus is also enumerable at JIT time.


II. Ecstasy to Java Classfile compiler (JIT) class naming conventions:

1. All Java interfaces produced by the JIT compiler extend "org.xtclang.ecstasy.Object"; all
   produced Java classes extend (directly or indirectly) "org.xtclang.ecstasy.nObject", which
   implements "org.xtclang.ecstasy.Object".

2. An Ecstasy type is a "Java-Primitive" type iff we choose to provide a second optimized
   representation of the type using a Java primitive value; for example: Int64 as long, Char as int,
   Boolean as boolean.

3. An Ecstasy type is an "XVM-Primitive" type iff we choose to implement it using two or more Java
   values (which at present are all of primitive Java types); for example Int128 as (long, long),
   Range<Int> as (long, long, boolean, boolean).

4. An Ecstasy type is a "JIT-Primitive" type iff it is a Java-Primitive type, an XVM-Primitive type,
   or the "Nullable" form of either.

5. For every Ecstasy type T there is a "JIT Call Class" JCC(T), such that:
    a) the JIT Call Class indicates the Java name of the classfile;
    b) the JIT Call Class indicates whether the classfile is a Java interface or a Java class;
    c) for any Ecstasy method with a parameter or return of type T, the corresponding standard Java
       signature will use the Java class or interface name provided by JCC(T); an optimized ("$p")
       signature may use the JIT-Shape of T instead;
    d) the "nObject.$xvmType()" method of every instance represented by JCC(T) will return a
       TypeConstant that will evaluate as "isA()" of the TypeConstant for type T;
    e) if JCC(T) indicates a Java class, then instances of that Java classfile can be cast to
       "org.xtclang.ecstasy.nObject" (even though the Ecstasy Object is technically an interface);
    f) all instances represented by JCC(T) can be cast to the "org.xtclang.ecstasy.Object"
       interface.

6. For every Ecstasy type T that represents an instantiable class (TypeInfo.isNewable method)
   there is a "JIT Instance Class" JIC(T), such that:
    a) the JIT Instance Class indicates the Java name of the instantiable classfile;
    b) "NEW*" ops for type T produce an instance of the Java class JIC(T) by invoking a "$new"
       static method (an "instantiator") on the JIC(T);
    c) when dealing with parameterized types, JIC(T) and JCC(T) may differ; when they differ:
        1) JCC(T) is non-instantiable i.e. abstract, and is either a Java class or interface;
        2) JIC(T) extends or implements the JCC(T).
    d) if JCC(T) is an abstract class, then the JIT additionally generates an equivalent interface
       by prefixing "i" to the class name, and the JCC(T) implements that interface;
    e) if T has a formal type parameter that cannot be resolved in the current build context and
       whose resolution can change JIC(T), then JIC(T) is not resolvable at JIT time and will be
       resolved at run time instead; for example, within a Map implementation where the Key type is
       not known at compile time, the code `new Key[]` will (typically) still be unresolved at JIT
       time, and the JIT must produce code that will use the runtime value of the type Key in order
       to calculate the JIC(Key[]); additional examples include the expression "new U[]" where U is
       a formal type provided to a method, or "new V()" where V is a formal type with the type
       constraint of Replicable; in these cases, the implementation will behave as if the formal
       types are resolved first, then the above steps (a-d) are followed.

7. For every instantiable-but-unresolved Ecstasy type T (as described in 6e above) that the JIT may
   need to implement "NEW*" ops for, the plan-of-record is as follows:
    a) an "instantiator interface" declares instance-method counterparts of the static instantiators,
       with standard and optimized variants as applicable. Its implementations on the class-of-class
       are called "instantiator routers";
    b) the JIT uses the JCC(T) to determine the approximate class to instantiate, which could in
       theory be the same as the JIC(T), but is likely to point to a super-class (or interface) of
       the JIC(T) as it would be resolved at runtime;
    c) to implement the "NEW*" ops, the JIT will produce code that resolves T at run time and
       obtains the class-of-class for JIC(T), accessed through the instantiator interface for
       JCC(T);
    d) the JIT invokes an instantiator router named "$new" on that object, passing the fully
       resolved T followed by the same arguments that will be passed to JIC(T).$new; see also the
       doc on the CommonBuilder.assembleNew method;
    e) the instantiator router on class-of-class invokes the "$new" static instantiator on JIC(T);
    f) ideally, the resolution of T and runtime JIC(T) calculation (in step c) and the
       indirect call to the JIC's "$new" static method (in step e) are emitted by this JIT in a
       manner that optimizes for repeated use of the same resolved T, via caching or other means;
    g) for virtual child construction, the JIT will first resolve the requested child type against
       the runtime type of its outer object, preserving the parent's resolved parameters and the
       child's own type arguments, then invoke the instantiator router for the resulting JIC(T),
       passing the outer object along with the constructor arguments; JIT will generate standard
       and optimized instantiator-interface methods and corresponding instantiator routers as
       applicable, so primitive arguments remain unboxed on the optimized path; the instantiator
       router will invoke the selected JIC's static "$new" directly, without runtime Java member
       lookup.

8. For an Ecstasy type T that is an interface, mixin, annotation or a pure type, there is no JIC(T)
   (since the type cannot be instantiated), and only a JCC(T) is generated, which is a Java
   interface. For an Ecstasy abstract class, (i) there is no JIC(T) and (ii) JCC(T) is an abstract
   Java class -- and an "i" interface thereof in the case of parameterized types subject to
   specialization.

9. In addition to the layer one specialization (see section I above), the JIT will use that same
   approach (generating those additional classes and interfaces, what we refer to internally as
   the "long arms" model) for two additional layers of specialization:
    a) each Ecstasy Object reference at runtime is implemented and represented by the JIT using a
       sequence of zero or more Java types, which can be expressed using Java type signature
       notation; for example, almost all Ecstasy types use (i.e. will be stored in, will be passed
       as) a single Java reference (e.g. "Lorg/xtclang/ecstasy/nObject;" or a sub-type thereof),
       while a few types are JIT-Primitive types that (mostly) use some combination of Java
       primitives, for example the Ecstasy "Int" using a Java long ("J"), and "UInt128?" using two
       Java longs and a boolean ("JJZ"); we call this the JIT-Shape (see the JitFlavor class);
    b) "layer two specialization" is produced by the JIT when any formal type parameter of a
       parameterized Ecstasy type can be resolved to different Ecstasy types that do not all have
       the same JIT-Shape; the specialization applies to fields and optimized ("$p") methods;
    c) "layer three specialization" refers to any additional explicit support necessary to map
       between the JIT-Shape and any more-specific representation of the Ecstasy type by the JIT;
       specifically, the "$box" and "$unbox" methods;
    d) layer two and three specialization are used whenever both of the following are true:
        1) the Ecstasy type is parameterized (has generic types);
        2) at least one of the generic types can be assigned from a JIT-Primitive type;
    e) as implied by point "b" above, the "long arms" overhead (generating additional classes and
       interfaces) may be completely avoided in cases where, for each type parameter, it is provable
       that all possible types for that type parameter will share the same exact single JIT-Shape.

10. With respect to specialization, the JIT will generate the following Java classes:
   a) when at least one generic type parameter is a JIT-Primitive type, the corresponding Java class
      or interface is called a "Specialized class" or "Specialized interface"; each Specialized
      class also has a corresponding "i"-prefixed Specialized interface that it implements;
   b) when no generic type parameter is a JIT-Primitive type, the produced Java class or interface
      is called a "Generalized class" or "Generalized interface";  each Generalized class also has a
      corresponding "i"-prefixed Generalized interface that it implements;
   c) with respect to one or more type parameters introduced by an Ecstasy class (etc.), we refer to
      the initial specialization level in the class hierarchy as "initial specialization", and
      subsequent inheritance from that level as "continued specialization";
   d) for all combinations of "a" and "b" above, a corresponding Java class or interface is created
      called the "Central class" or "Central interface"; a Central class is only created as part of
      the initial specialization, is abstract, and implements the Central interface; every
      Specialized and Generalized class at the initial specialization level extends the Central
      class; every Specialized and Generalized interface at each specialization level extends the
      Central interface of that level; every Central interface of a continued specialization level
      extends the Central interface of the level above it; at a continued specialization level,
      every Specialized and Generalized interface also extends the corresponding interface from the
      level above it, and every Specialized and Generalized class extends the corresponding class
      from the level above it;
   e) a "JIT-Column" is the sequence of corresponding generalized, specialized, or central artifacts
      across continued specialization levels; a JIT-Column extends vertically as far as there are
      specialization levels containing that specialization; in "long-arms" jargon, the central
      column is referred to as the "spine" or "trunk";
   f) for layer one specialization, the JIT emits Generalized interfaces for each variant; for
      example, iRange<Orderable> and iRange<Sequential>;
   g) layer two and three specialization are combined into a single set of emitted classes and
      interfaces; for example, the Central interface iRange, the Specialized interfaces
      iRange<Int32> and iRange<Int64>, the Specialized classes Range<Int32> and Range<Int64>, and
      the Generalized classes Range<Orderable> and Range<Sequential> (i.e. the JIT Shape is a Java
      reference);
   h) the absence of an abstract class representing ranges of all Orderable types and an abstract
      class representing ranges of all Sequential types is a conscious decision; similarly, the
      absence of a distinct layer two Specialization based solely on JIT Shapes is also a conscious
      decision; in both cases, we accept additional unnecessary replication of code, and if we later
      realize that we dislike the resulting trade-offs, the design should be easily modifiable.

   Note: Specializable Ecstasy types always have a single underlying class (as defined by the
         TypeConstant.isSingleUnderlyingClass() API)

   Example:
     If a Specializable Ecstasy type D<T1, T2, T3> extends a Specializable Ecstasy type B<T1, T2>,
     then JCC(D<T1, T2, T3>) extends JCC(B<T1, T2>) in the corresponding JIT-Column. If only T3 is a
     JIT-Primitive type, JCC(D<T1, T2, T3>) is Specialized while JCC(B<T1, T2>) is Generalized.
     If a Specializable Ecstasy type D<T1, T2, T3> extends a non-Specializable Ecstasy type
     B<T1, T2>, then D is an initial specialization; JCC(D<T1, T2, T3>) extends the Central JCC(D),
     which extends JCC(B<T1, T2>).

III. Virtual child classes: hard-left implementations and composition-specific super

A "base child" is a virtual child with no same-name super child inherited through its enclosing
parent's hierarchy. Base children occupy the leftmost column in the diagrams below and are called
"hard-left" classes. A "derived child" has a same-name super child, whether or not the derived parent
explicitly declares the child. These terms describe inheritance through the parent hierarchy, not
inheritance between differently named children.

1. Consider parent classes B and D, where D extends B. B declares virtual children C0 and C1,
   with C1 extending C0; D can override either child. The Ecstasy subtype relationships are:

       B.C0 <--- D.C0
        ^         ^
        |         |
       B.C1 <--- D.C1

   Both B.C0 and B.C1 are hard-left classes, despite B.C1 extending B.C0. D.C0 and D.C1 are derived
   children, with same-name super children B.C0 and B.C1; D.C1 remains a derived child even if D
   does not explicitly declare C1. Further parent inheritance extends this diagram to the right;
   further child inheritance extends it downward.

   The Java implementation classes preserve inheritance between hard-left classes and inheritance
   from same-name super children. Using symbolic Java names, where B_C0 denotes JIC(B.C0):

       class B_C1 extends B_C0
       class D_C0 extends B_C0
       class D_C1 extends B_C1

   Thus, a D_C1 receiver is a Java B_C1 and B_C0, but is NOT a Java D_C0. Preserving the hard-left
   inheritance is a requirement: it makes concrete hard-left receiver types safe for all these
   compositions.

2. Hard-left callable types use their implementation classes: JCC(B.C0) = B_C0 and
   JCC(B.C1) = B_C1. Derived-child callable types use interfaces: JCC(D.C0) = D_iC0 and
   JCC(D.C1) = D_iC1. Every child also has an explicit interface contract, including hard-left
   classes. The corresponding contracts are:

       interface B_iC1 extends B_iC0
       interface D_iC0 extends B_iC0
       interface D_iC1 extends B_iC1, D_iC0

   Each implementation class implements its corresponding child interface. D_C1 can therefore
   be passed as D_iC0 without being cast to the unrelated implementation class D_C0. Parameters,
   returns, properties, and method handles consistently use callable descriptors. Standard and
   optimized signatures follow the same specialization rules as other JCC/JIC pairs.

   The "super-router" signatures define stable continuation points for super calls whose next body
   depends on the runtime parent composition. For example, super() in B.C1.foo() must enter
   B.C0.foo() on a B.C1 receiver, but D.C0.foo() on a D.C1 receiver. A separate virtual
   super-router method selects that continuation without restarting ordinary foo() dispatch or
   recompiling B.C1. Its explicit interface receiver lets the selected detached body operate on
   the same object even when that object is not an instance of the body's Java implementation class,
   as with D_C1 and D_C0.

   Ordinary hard-left calls use concrete class dispatch. Super-router signatures explicitly use the
   hard-left class's interface contract, not its JCC, so their descriptors remain stable along parent
   inheritance. Converting a derived-child interface reference to a hard-left class requires a
   Java checkcast even though the corresponding Ecstasy subtype relationship is valid.

3. Every hard-left class generates all applicable virtual instance methods, including accessors,
   whether or not the Ecstasy class declares them. Required standard and optimized entry points
   are both generated. An inherited concrete method gets a trivial forwarding body:

       return super(args);

   An abstract method without an implementation remains abstract; private methods, functions, and
   constructors are not made virtual by this rule.

   The forwarding hard-left body establishes a method boundary even when the Ecstasy method
   chain contains no declared body at that class. It must not simply inherit the Java method from
   the preceding hard-left class, because doing so could bypass an intervening derived-child body.

   For example, suppose B.C0 declares foo(), B.C1 merely inherits it, and both D.C0 and D.C1
   override foo() with super calls. Java D_C1 extends B_C1, not D_C0. If B_C1 simply inherits
   foo(), ordinary Java super dispatch from D_C1 would reach B_C0.foo(), skipping D.C0.foo().
   Generating a forwarding B_C1.foo() establishes the missing boundary: its super$C0$foo
   continuation selects D.C0.foo() for the D_C1 receiver, which then calls B.C0.foo().

   A super() call from a hard-left body uses a virtual super-router method rather than
   a fixed Java super call. The caller has a concrete receiver (B_C1 for B.C1 or B_C0 for B.C0),
   which is valid for a D_C1 object, so the super-router call can use ordinary Java class
   dispatch.

   Functions remain static. Direct calls, function handles, and class-of-class funky routes select
   the implementing child's Impl at compile time, even when it lies outside the target's Java
   inheritance chain. For example, a call to D.C1.f() inherited from D.C0 targets D_C0.f(...).

   Private instance methods are also bound to their exact declarations at compile time. Calls and
   bound-method handles target the detached body on the declaring child's Impl directly. For example,
   a body declared on D.C0 can execute on a D.C1 receiver and call its own private method D.C0.f()
   through D_C0.s$f(D_iC0 receiver, ...); no private-method router is required.

4. Each virtual child implementation generates virtual Java super-router methods for the
   applicable Ecstasy method entries that can be reached by a super call. The name concatenates the
   target child name and Java method name: super$<childName>$<JavaMethodName> (e.g. super$C0$foo).
   Standard and optimized variants follow the corresponding Java signatures and names, such as
   super$C0$foo$p; the full method descriptor distinguishes overloads.

   A "detached body" is a static method on the child's implementation class, e.g.
   D_C0.s$foo(D_iC0 receiver, Ctx ctx), that contains the actual Ecstasy code for a virtual child
   instance method foo(), with its receiver passed explicitly. The static method's owner and its
   receiver type are separate: the Impl shape owns every detached body; the Pure shape declares
   the instance method contract but does not contain its detached body.

   For a non-hard-left implementation, the receiver is always declared as the child interface.
   A valid Ecstasy receiver need not belong to the corresponding Java implementation class:
   D_C1 implements D_iC0 but does not extend D_C0. Therefore D.C0.foo() runs through
   D_C0.s$foo(D_iC0 receiver, Ctx, ...), without requiring the receiver to be a Java D_C0.

   Hard-left implementations do not have this receiver mismatch: the Java inheritance hierarchy
   guarantees that their concrete receiver types remain valid in derived parent compositions.
   The current implementation also emits hard-left bodies as detached bodies with concrete
   receivers for uniformity; only non-hard-left implementations require interface receivers.

   The ordinary virtual foo() method routes to the detached body at the head of the effective
   method chain. A super-router method instead routes to the detached body selected as the
   next step of a super() call. Both contain only routing code, not a copy of the Ecstasy body.

   Both entrances use Java virtual dispatch, but differ in which overrides participate. When D.C0
   and D.C1 both declare foo(), ordinary foo() and super$C0$foo select D.C0.foo() on a D_C0
   receiver. On a D_C1 receiver, however, ordinary foo() selects D.C1.foo(), even when called
   through a D_iC0 interface reference, while super$C0$foo selects D.C0.foo(). The latter dispatches
   to D_C1.super$C0$foo, which calls D_C0.s$foo; Java cannot dispatch directly to D_C0.foo()
   because D_C1 does not extend D_C0. Thus, a super-router method selects a body for a particular
   child name within the chain, not the head of the complete chain, and cannot generally replace the
   ordinary virtual entrance.

   A super-router method takes an explicit interface receiver, followed by the context and method
   arguments. It routes to the exact detached body selected by the receiver's effective
   TypeInfo and optimized method chain, returning its result or just calling it for a
   void method. The implicit Java dispatch receiver and explicit body receiver are the same object;
   no delegate is involved.

   The super-router descriptor remains identical along parent inheritance. In particular, a
   receiver parameter declared as B_iC0 must not become D_iC0 in an override: that would be an
   overload, not an override. The overriding route casts the receiver to the interface required by
   its target body. For a void foo(), the generated methods are:

       // on B_C1
       void super$C0$foo(B_iC0 thi$, Ctx ctx) {
           B_C0.s$foo((B_C0) thi$, ctx);
       }

       // on D_C1
       @Override
       void super$C0$foo(B_iC0 thi$, Ctx ctx) {
           D_C0.s$foo((D_iC0) thi$, ctx);
       }

   A super() call in the hard-left B.C1.foo() body becomes:

       thi$.super$C0$foo(thi$, ctx);

   Virtual dispatch selects B.C0.foo() on a B_C1 object and D.C0.foo() on a D_C1 object. The same
   rule applies to super() calls in the synthesized forwarding bodies described above, even when
   B.C1 has no declared Ecstasy body. This super() dispatch uses the caller's concrete receiver;
   it does not need interface dispatch or knowledge of derived parents.

5. Derived-child bodies use interface-compatible receivers so a child's body can execute on an
   instance of a differently named child.

   For example, D.C0.foo() can execute on a D_C1 object through a D_iC0 receiver. Its super target
   is fixed at B.C0.foo(); it does not need a composition-specific super-router call. Likewise,
   the super target of D.C1.foo() is B.C1.foo(). With E extending D, E.C0.foo() has the fixed
   predecessor D.C0.foo(), and E.C1.foo() has D.C1.foo().

   "Fixed super" means entering the exact predecessor body, not calling the ordinary virtual
   method again. A Java super invocation can be used where the JVM receiver/owner relationship
   permits it. An interface-compatible body instead uses an exact body entry point, for example a
   detached body with an explicit receiver. Casts to hard-left implementation ancestors are valid;
   casting a D_C1 receiver to D_C0 is not.

   The corresponding detached body signatures are:

       B_C0.s$foo(B_C0 thi$, Ctx ctx)           // concrete hard-left body
       B_C1.s$foo(B_C1 thi$, Ctx ctx)           // concrete hard-left body
       D_C0.s$foo(D_iC0 thi$, Ctx ctx)          // interface-compatible derived-child body
       D_C1.s$foo(D_iC1 thi$, Ctx ctx)          // interface-compatible derived-child body

   The Ecstasy method remains virtual; detached bodies are exact implementation call targets,
   not a change to its language-level calling convention. Ordinary virtual calls select the head
   of the composition chain. Fixed super calls select a particular body without restarting that
   dispatch.

   For example, super() inside D_C0.s$foo calls B_C0.s$foo((B_C0) thi$, ctx) directly. It must
   not call super$C0$foo again, which on a D_C1 object would re-enter D.C0.foo().

           | invokestatic; pass r as D_iC1
           v
       D_C1.s$foo(D_iC1 r, Ctx ctx)                   [Ecstasy D.C1.foo() code]

   super() calls: continue from that implementation without restarting ordinary foo() dispatch

   Ecstasy (inside D.C1):

       @Override
       void foo() {
           super();
       }

   Generated Java call path:

       D_C1.s$foo(D_iC1 r, Ctx ctx)                   [Ecstasy D.C1.foo() code]
           |
           | super(): fixed invokestatic; cast r to B_C1
           v
       B_C1.s$foo(B_C1 r, Ctx ctx)                    [hard-left Ecstasy B.C1.foo() code]
           |
           | super(): invokevirtual B_C1.super$C0$foo(B_iC0, Ctx)
           | Java dispatch selects the D_C1 override
           v
       D_C1.super$C0$foo(B_iC0 r, Ctx ctx)             [super-router; routing only]
           |
           | invokestatic; cast r to D_iC0
           v
       D_C0.s$foo(D_iC0 r, Ctx ctx)                   [Ecstasy D.C0.foo() code]
           |
           | super(): fixed invokestatic; cast r to B_C0
           v
       B_C0.s$foo(B_C0 r, Ctx ctx)                    [hard-left Ecstasy B.C0.foo() code]

   In the super-router method, Java's implicit this and the explicit receiver argument are both r.
   The casts only change its Java type view; no separate D_C0 object is involved. Results return
   along the call path. Optimized variants use the same routes with the corresponding $p signatures.

   The compiled B_C1 body is unchanged; generating D_C1 does not rewrite or recompile a
   previously loaded B_C1 class.

   Another required case is:

       B.C0 declares foo(); B.C1 inherits it
       D.C0 overrides foo(); D.C1 inherits it

   B_C1 still generates foo() under rule 3. Its forwarding body calls super$C0$foo, which on D_C1
   enters D.C0.foo(), followed by B.C0.foo(). The synthetic forwarding body adds no Ecstasy behavior,
   but prevents Java inheritance from skipping the D.C0 override.

7. A bound super function captures the same receiver and the same successor that a direct super call
   would use. Binding super in a hard-left body binds its virtual super-router method and explicit
   receiver argument, preserving composition-specific dispatch. Binding super in a derived-child
   body binds its fixed predecessor body entry. Neither case binds the ordinary virtual method at
   the head of the chain.

   Nested instance methods and capturing lambdas use the enclosing detached body's receiver type
   and are emitted as static methods on the same implementation class. Ordinary bound methods
   still use the callable contract, so binding a D.C0 method on a D_C1 object does not require a
   D_C0 receiver.

8. Storage follows the effective composition, not merely the chosen Java superclass. If D.C0
   introduces a backing field, a D_C1 implementation needs that storage even though it does not
   extend D_C0. Its struct TypeInfo determines the required fields; fields already supplied by the
   Java implementation hierarchy are reused, and missing fields are generated locally.

   Interface-compatible bodies access backing storage through synthetic raw field accessors.
   These are distinct from Ecstasy property getters/setters and do not introduce their custom
   behavior or mutability checks into struct access. Hard-left bodies can use direct field access
   for their concrete receiver types.

   Construction, field initialization, and validators must use the same actual object and obey
   the same receiver rules. Struct writes still bypass ordinary setters. Calls to private methods
   target detached bodies on the declaring child's Impl class, without virtual dispatch. Identity,
   the "outer" reference, runtime type, and mutable state belong to one object; no separate D_C0
   delegate is constructed for D_C1.

9. A missing child declaration does not imply an unchanged composition. If D overrides C0 but
   does not declare C1, D.C1 can still require different super-router routes, callable contracts,
   and storage. Construction must select an implementation of that effective composition, not
   blindly instantiate the first ancestor with a declared C1.

   An inherited implementation can be reused when its callable contracts, field layout, and
   method chains are equivalent. Otherwise, a composition-specific JIC is required even without
   a new Ecstasy child declaration. Such an implementation contains the necessary routes and
   storage; it is not an unconditional empty phantom class.

10. Bodies are reusable within the required JIT specialization; parent compositions supply the
    differing super-router routes and storage accessors. Runtime calls use generated methods,
    rather than searching a method-chain table on every call. The design does not require changing
    Ecstasy op production: TypeInfo describes the composition, and the ops identify the operations
    and source contributions to compile.


IV. Test coverage for virtual classes

Regression tests should cover teh following scenarios:
    a) the same receiver passed as both B.C1 and D.C0, with identity preserved;
    b) declared and synthesized hard-left methods, including the inherited case in rule 6;
    c) fields introduced by D.C0 and accessed on D.C1, private methods, and returning "this";
    d) ordinary virtual calls from inside a body versus direct and bound super calls;
    e) constructors, field initializers, and validators acting on that same storage;
    f) missing C0 or C1 declarations and additional parent and child inheritance levels;
    g) generic children and the standard/optimized signatures required by their JIT shapes.


V. Annotation classes

1. Consider the following Ecstasy topology:
        class B implements I {}
        annotation A0 into I {}
   and a composition "@A0 B".

   The JIT compiler will create the following Java classes:
        a) an interface JCC(I);
        b) an interface JCC(A0) that extends JCC(I);
        c) a class JIC(B) that implements JCC(I);
        d) a class JIC(@A0 B), whose name may look like ""@A0$B#N" that extends JIC(B), implements
           JCC(A0) (and JCC(I) by implication); N refers to the cannonical annotated type with
           annotation parameters stripped

2. Applying multiple annotations produces multiple implementation classes. For the composition of
   "@A1 @A0 B" (where A1 is also "into I") JIT will additionally produce
        a) an interface JCC(A1) that extends JCC(I);
        b) a class JIC(@A1 @A0 B), whose name may look like ""@A1@A0$B#N" that extends JIC(B),
           and implements JCC(A1) and JCC(A0)

3. Consider now a derived "class D extends B" and a composition "@A0 D". In addition to (1), the JIT
   will produce
        a) a class JIC(D) that extends JIC(B);
        b) a class JIC(@A0 D), whose name may look like ""@A0$D#N" that extends JIC(D), implements
           JCC(A0)

4. As indicated by above, JIC(@A0 D) extends JIC(D), not JIC(@A0 B). Nevertheless, @A0 D is an
   Ecstasy subtype of @A0 B, so an @A0 B reference must accommodate objects of either implementation
   class and its callable Java representation therefore cannot generally be JIC(@A0 B).

   Instead, references to annotated compositions use the Widened flavor. As with long-arm
   specialization, JCC(T) and JIC(T) need not be the same: the full Ecstasy type is retained, while
   widened locals, fields, parameters, and returns use an existing common Java reference type.
   Java casts use JCC(T), not JIC(T); the callable representation must accommodate all compatible
   implementations. Moreover, no callable interface for each annotation combination is needed.
   Before invoking a method or property accessor, the JIT casts the receiver to the existing class
   or interface supplying the callable contract: JCC(B) for a B member, JCC(A0) for an A0 member
   and so on.

5. An annotated instantiator always accepts the exact TypeConstant immediately after Ctx, even
   when the underlying class has no generic parameters. An outer object, when required, follows
   the type. The remaining arguments concatenate the base constructor parameters with those of
   each selected annotation constructor, in leading annotation order:

       $new(Ctx ctx, TypeConstant type, [outer], baseArgs..., A1Args..., A0Args...)

6. Construction follows the ordinary class construction lifecycle on a single receiver. The
   Java initializer chain initializes base and annotation fields, and the exact runtime type is
   retained on that receiver. Annotation constructor bodies then run in leading annotation order,
   followed by the selected base constructor body. For @A1 @A2 C, the constructor-body order is
   A1, A2, B (the base constructor runs last).

   Annotation constructor bodies are generated as synthetic static methods on the incorporating
   implementation.

   Validators run after all constructor bodies, using the effective TypeInfo's validator chain,
   including annotation validators. Field verification, post-construction work, and constructor
   finalizers remain part of the ordinary construction lifecycle; annotations do not introduce
   a separate object lifecycle or change which object owns identity and state.

7. For an annotated virtual child, the runtime outer object selects the effective child before
   the implementation class is chosen. Resolving the child preserves the requested annotations
   and the resolved parent and child type parameters. The resolved type's JIC name identifies
   the implementation class; Ctx.classForType(type) can obtain that Java class through its owning
   module loader.

   Every selected annotated child implementation must provide the corresponding instantiator
   shape. Its constructor-specific name and base-child return descriptor remain stable across
   runtime child overrides, while its parameters include the exact annotated type, outer object,
   base arguments, and annotation arguments as described in (5).

   The resulting reference follows the Widened rule in (4); member calls cast to the existing
   child or annotation JCC as appropriate, not a new interface for the annotated composition.
   The underlying child's inheritance and dispatch follow the ordinary virtual-child rules in
   section III, with no additional annotation-specific distinction between hard-left and derived
   children.


VI. Test coverage for annotated classes

Regression tests should cover the following scenarios, using assertions for observable behavior
and generated-class inspection for Java naming, inheritance, and calling conventions:
    a) a single annotation into a class or interface, multiple annotations in both orders, and
       annotations that implement additional interfaces; calls through the base, annotation, and
       contributed interfaces must reach the effective implementation;
    b) class-declaration ("built-in") annotations, as used by @PeekAhead on ObjectInputStream's
       ElementInputStream and ArrayInputStream classes in lib_json; ordinary construction must
       include the annotation's overrides, and adding @CloseCap or @PointerAware at the new site
       must preserve PeekAhead's behavior and access to the same outer ObjectInputStream;
    c) widened locals, fields, parameters, and returns holding both @A B and @A D, where D extends
       B; base and annotation methods, property accessors, and bound methods must work on the same
       receiver without casting to a particular annotated implementation class;
    d) positive and negative is/as checks through Object, the base type, and annotation types,
       including differently annotated compositions with the same widened Java representation;
       checks must validate the full Ecstasy type rather than only the erased Java descriptor;
    e) every combination of base and annotation constructor overloads, including overloads whose
       distinct Ecstasy parameter types share a Java descriptor, such as Int and UInt; test
       constant and register arguments, omitted defaults, explicit Null, and no-op constructors;
    f) standard and optimized constructor paths with reference, primitive, nullable primitive, and
       multi-slot arguments, including a standard base constructor with an optimized annotation
       constructor and the reverse; argument concatenation and slot offsets must remain correct;
    g) field initializers, annotation constructor bodies in leading annotation order, the base
       constructor body, validators, and finalizers; verify the order, rejection of invalid state,
       and shared identity and storage throughout construction;
    h) annotation overrides and super calls, including inherited base implementations, calls from
       inside annotation bodies, and bound methods; additional annotations must participate in the
       effective method chain without introducing a separate receiver;
    i) generic base classes and annotations across generalized and specialized representations;
       different annotation argument values must reuse the canonical JIC while each instance
       retains its exact runtime type and values, and different annotation compositions must
       receive the appropriate implementation classes;
    j) annotated virtual children constructed inside and outside the outer class, including a
       base-typed outer reference to a derived parent; preserve the annotations, resolved parent
       and child type arguments, outer identity, and base-child return contract while selecting
       the effective child implementation and dispatch described in section III.
