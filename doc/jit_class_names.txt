I. Ecstasy composition specialization:

1. Composition specialization refers to the ability for an Ecstasy type that declares one or more
   type parameters and is composed with one or more conditional incorporations to be specialized in
   terms of its composition based on a combination of (i) the types specified for those type
   parameters, and (ii) the set of conditional incorporations that occur based on those specified
   types. For example, the Range class implies two specializations: (0) when Element is NOT
   Sequential, and (1) when Element IS Sequential. For example, the ListMap class implies four
   specializations: (00) when Key is NOT immutable Hashable and Value is NOT Shareable, (01) when
   Key IS immutable Hashable and Value is NOT Shareable, (10) when when Key is NOT immutable
   Hashable but Key IS immutable Object and Value IS Shareable, and (11) when Key IS immutable
   Hashable and Value IS Shareable.

2. For the JIT project, Ecstasy composition specialization is the first step of specialization,
   referred to as "layer one specialization". This corresponds to the minimum set of TypeInfo
   objects that must be calculated for an instantiable class; for example, Range requires only 2
   TypeInfo objects to be calculated ("private Range<Orderable>" and "private Range<Sequential>"),
   and ListMap requires 4 TypeInfo objects to be calculated ("private ListMap<Object, Object>",
   "private ListMap<immutable Hashable, Object>",  "private ListMap<immutable Object, Shareable>",
   and "private ListMap<immutable Hashable, Shareable>"). Each type parameter in these examples is
   calculated as the intersection of the class' parameter constraint type (such as Orderable in the
   Range example) with each of the applied conditional incorporation parameter constraint types
   ("immutable Object" and "immutable Hashable" in the Listmap "11" case).

3. For each layer one specialization of Ecstasy types, the JIT will produce a "class of" ("c"
   prefix) classfile and an "interface of" ("i" prefix) classfile.

4. It is worth stating: the resulting set of layer one specialized compositions is enumerable at
   Ecstasy compile-time, and thus is also enumerable at JIT time.

II. Ecstasy to Java Classfile compiler (JIT) class naming conventions:

1. All Java interfaces produced by the JIT compiler extend "org.xtclang.ecstasy.Object"; all
   produced Java classes extend (directly or indirectly) "org.xtclang.ecstasy.nObject", which
   implements "org.xtclang.ecstasy.Object".

2. An Ecstasy type is a "Java-Primitive" type iff we choose to provide a second optimized
   representation of the type using a Java primitive value; for example: Int64 as long, Char as int,
   Boolean as boolean.

3. An Ecstasy type is an "XVM-Primitive" type iff we choose to implement it using two or more Java
   values (which at present are all of primitive Java types); for example Int128 as (long, long),
   Range<Int> as (long, long, boolean, boolean).

4. An Ecstasy type is a "JIT-Primitive" type iff it is a Java-Primitive type, an XVM-Primitive type,
   or the "Nullable" form of either.

5. For every Ecstasy type T there is a "JIT Call Class" JCC(T), such that:
    a) the JIT Call Class indicates the Java name of the classfile;
    b) the JIT Call Class indicates whether the classfile is a Java interface or a Java class;
    c) for any Ecstasy method with a parameter or return of type T, the corresponding Java signature
       will use the Java class or interface name provided by JCC(T);
    d) the "nObject.$xvmType()" method of the classfile specified by JCC(T) will return a
       TypeConstant that will evaluate as "isA()" of the TypeConstant for type T;
    e) if JCC(T) indicates a Java class, then instances of that Java classfile can be cast to
       "org.xtclang.ecstasy.nObject" (even though the Ecstasy Object is technically an interface);
    f) all classfiles indicated by JCC(T) can be cast to the "org.xtclang.ecstasy.Object" interface.

6. For every Ecstasy type T that represents an instantiatable class (TypeInfo.isNewable method)
   there is a "JIT Instance Class" JIC(T), such that:
    a) the JIT Instance Class indicates the Java name of the instantiable classfile;
    b) "NEW*" ops for type T produce an instance of the Java class JIC(T) by invoking a "$new"
       static method on the JIC(T);
    c) when dealing with parameterized types, JIC(T) and JCC(T) may differ; when they differ:
        1) JCC(T) is non-instantiable i.e. abstract, and is either a Java class or interface;
        2) JIC(T) extends or implements the JCC(T).
    d) if JCC(T) is an abstract class, then the JIT additionally generates an equivalent interface
       by prefixing "i" to the class name, and the JCC(T) implements that interface;
    e) if T has a formal type parameter, then JIC(T) is not resolvable at compile or JIT time and
       will be resolved at run time instead; for example, within a Map implementation where the Key
       type is not known at compile time, the code `new Key[]` will (typically) still be unresolved
       at JIT time, and the JIT must produce code that will use the runtime value of the type Key in
       order to calculate the JIC(Key[]); additional examples include the expression "new U[]" where
       U is a formal type provided to a method, or "new V()" where V is a formal type with the type
       constraint of Replicable; in these cases, the implementation will behave as if the the formal
       types are resolved first, then the above steps (a-d) are followed.

7. For every instantiable-but-unresolved Ecstasy type T (as described in 6e above) that the JIT may
   need to implement "NEW*" ops for, the plan-of-record is as follows:
    a) The JIT uses the JCC(T) to determine the approximate class to instantiate, which could in
       theory be the same as the JIC(T), but is likely to point to a super-class (or interface) of
       the JIC(T) as it would be resolved at runtime;
    b) To implement the "NEW*" ops, the JIT will produce code that invokes a virtual method on the
       "class of class" for the JIC(T) (a class of the same name but prefixed with "c"), with a
       method name "$dnew" that corresponds to the JIC's "$new" static method, passing the same set
       of arguments that will be passed to the JIC's "$new" described in section 6 above; see also
       the doc on the CommonBuilder.assembleNew method;
    c) the "$dnew" method on the class-of-class for the JCC(T) receives a fully resolved T that is
       used to dynamically (hence the "d" in "$dnew") determine the JIC(T);
    d) the "$dnew" method on the class-of-class for the JCC(T) invokes the "$new" static method on
       JIC(T);
    e) ideally, the resolution of T (in step b), the runtime JIC(T) calculation (in step c), and the
       indirect call to the JIC's "$new" static method (in step d) are emitted by this JIT in a
       manner that optimizes for repeated use of the same resolved T, via caching or other means.

8. For an Ecstasy type T that is an interface, mixin, annotation or a pure type, there is no JIC(T)
   (since the type cannot be instantiated), and only a JCC(T) is generated, which is a Java
   interface. For an Ecstasy abstract class, (i) there is no JIC(T) and (ii) JCC(T) is an abstract
   Java class -- and an "i" interface thereof in the case of parameterized types subject to
   specialization.

9. In addition to the layer one specialization (see section I above), the JIT will use that same
   approach (generating those additional classes and interfaces, what we refer to internally as
   the "long arms" model) for two additional layers of specialization:
    a) each Ecstasy Object reference at runtime is implemented and represented by the JIT using a
       sequence of zero or more Java types, which can be expressed using Java type signature
       notation; for example, almost all Ecstasy types use (i.e. will be stored in, will be passed
       as) a single Java reference (e.g. "Lorg/xtclang/ecstasy/nObject;" or a sub-type thereof),
       while a few types are JIT-Primitive types that (mostly) use some combination of Java
       primitives, for example the Ecstasy "Int" using a Java long ("J"), and "UInt128?" using two
       Java longs and a boolean ("JJZ)"; we call this the JIT-Shape (see the JitFlavor class);
    b) "layer two specialization" is produced by the JIT when any formal type parameter of a
       parameterized Ecstasy type can be resolved to different Ecstasy types that do not all have
       the same JIT-Shape; the specialization applies to fields and optimized ("$p") methods;
    c) "layer three specialization" refers to any additional explicit support necessary to map
       between the JIT-Shape and any more-specific representation of the Ecstasy type by the JIT;
       specifically, the "$box" and "$unbox" methods;
    d) layer two and three specialization are used whenever both of the following are true:
        1) the Ecstasy type is parameterized (has generic types);
        2) at least one of the generic types can be assigned from a JIT-Primitive type;
    e) as implied by point "b" above, the "long arms" overhead (generating additional classes and
       interfaces) may be completely avoided in cases where, for each type parameter, it is provable
       that all possible types for that type parameter will share the same exact single JIT-Shape.

10. With respect to specialization, the JIT will generate the following Java classes:
   a) when at least one generic type parameter is a JIT-Primitive type, the corresponding Java class
      or interface is called a "Specialized class" or "Specialized interface"; each Specialized
      class also has a corresponding "i"-prefixed Specialized interface that it implements;
   b) when no generic type parameter is a JIT-Primitive type, the produced Java class or interface
      is called a "Generalized class" or "Generalized interface";  each Generalized class also has a
      corresponding "i"-prefixed Generalized interface that it implements;
   c) with respect to one or more type parameters introduced by an Ecstasy class (etc.), we refer to
      the initial specialization level in the class hierarchy as "initial specialization", and
      subsequent inheritance from that level as "continued specialization";
   d) for all combinations of "a" and "b" above, a corresponding Java class or interface is created
      called the "Central class" or "Central interface"; a Central class is only created as part of
      the initial specialization, and is abstract; every Specialized and Generalized class at the
      initial specialization level extends the Central class; every Specialized and Generalized
      interface at each specialization level extends the Central interface of that level; every
      Central interface of a continued specialization level extends the Central interface of the
      level above it;
   e) in a JIT continued specialization level, each generalization, specialization, and central
      class or interface that occurs in the continued specialization level and also exists in the
      level above or below it is referred to as a "JIT-Column"; a JIT-Column extends vertically as
      far as there are specialization levels containing that specialization; in "long-arms" jargon,
      the central column is referred to as the "spine" or "trunk";
   f) for layer one specialization, the JIT emits Generalized interfaces for each variant; for
      example, iRange<Orderable> and iRange<Sequential>;
   g) layer two and three specialization are combined into a single set of emitted classes and
      interfaces; for example, the Central interface iRange, the Specialized interfaces
      iRange<Int32> and iRange<Int64>, the Specialized classes Range<Int32> and Range<Int64>, and
      the Generalized classes Range<Orderable> and Range<Sequential> (i.e. the JIT Shape is a Java
      reference);
   h) the absence of an abstract class representing ranges of all Orderable types and an abstract
      class representing ranges of all Sequential types is a conscious decision; similarly, the
      absence of a distinct layer two Speciailization based solely on JIT Shapes is also a conscious
      decision; in both cases, we accept additional unnecessary replication of code, and if we later
      realize that we dislike the resulting trade-offs, the design should be easily modifiable.

   Note: Specializable Ecstasy types always have a single underlying class (as defined by the
         TypeConstant.isSingleUnderlyingClass() API)

   Example:
     If a Specializable Ecstasy type D<T1, T2, T3> extends a Specializable Ecstasy type B<T1, T2>
     and at least one of the generic types is JIT-Primitive then the corresponding Specialized Java
     class J(D<T1, T2, T3>) extends the Specialized Java class J(B<T1, T2>).
     If a Specializable Ecstasy type D<T1, T2, T3> extends a non-Specializable Ecstasy type
     B<T1, T2>, the Specialized Java class J(D<T1, T2, T3>) extends the Generalized J(D).

       class C<T0, T1>

===== Work pad =====

assume 3x Ecstasy types
 - some A (might be Object, might be some abstract or non-abstract base class)
 - some B<T> : A    where B is for "Base" class
 - some D<T> : B<T> where D for "Derived" class

 JIT produces:


                                              class A

                                                 ^
                                                 |

interface iB<Object>                     ~~> interface iB             <~~ interface iB<Int>
class B<Object> implements iB<Object>    --> abstract B implements iB <-- class B<Int>        "the shoulders"

        ^                                        ^                             ^
        |                                        |                             |              "long arms"

interface iD<Object>                     ~~> interface iD extends IB  <~~ interface iB<Int>
class D<Object> implements iB<Object>,iD<Object>                          class D<Int> implements iB<Int>,iD<Int>

-------------------------------------        -----------------------      --------------------------
Genericized Column                           Central Column               Specialized Column

class C {
    void foo(Range<Person> range) {...}
    void bar(Range range) {...}
    <T> Range<T> baz(T t1, T t2) {
        return new Range<T>(t1, t2);
    }

class C {
    void foo(Ctx ctx, Range<Orderable> range) {...} // or (Ctx ctx, Range#0 range)

    Range baz(Ctx ctx, nType type, Orderable t1, Orderable t2) {
        return Range.new$(ctx, type, t1, t2);
    }
}

        ...
    }
