JIT service architecture

I. Fibers and scheduling


II. Ecstasy to Java Classfile compiler (JIT) class naming conventions:

1. An Ecstasy service is considered to have a "membrane" separating the "outside" services from the
   "inside" context. Every Ecstasy service produces at least two Java classes:
   a) the service class proper (SC), containing the actual natural implementation (e.g. Registry)
   b) a service proxy (SP) that extends SC (e.g. pRegistry) and overrides every single SC method on
      the underlying class by passing the request onto the service (see section 5 below).
      This method is called Async Call Router (ACR).

2. A JIT generated Service class extends nService and always belongs to (runs in the context of) its
   parent Container.

3. Service instantiation (construction) follows this plan:
    a) the corresponding SC gets instantiated and provided the parent container and gets
       registered (via a WeakReference) with that container;
    b) a proxy instance gets instantiated and returned to the caller.

4. The service method calling sequence:
    a) we need to add a "boolean async" parameter to every method call, so the signature of every
       method generated by JIT starts with either (Ctx ctx, boolean async) for standard methods
       or (Object this$, Ctx ctx, boolean async) for detached ones;
    b) when a ACR is called with the "async" value of "true", it is allowed to return a default
       value (null or 0) on Java stack while providing the corresponding future through the Ctx.
    c) we need to introduce a concept of a "pass-through" register, which is a register that may
       or may not be a recipient of an asynchronous return value; to accomplish this we need to
       add a new op (VAR_P) that will be recognized by the JIT compiler;

       (Implementation note: this op will be added by the ReturnStatement.emit() when the underlying
       expressions are InvocationExpressions.)
    d) if the JIT compiler determines that if the recepient of the return value(s) for an invocation
       is a register of a "Future" type, it passes "true" as the value of that the "async" parameter;
       otherwize, if the recepient is a pass-through register, it simply copies the value of the
       incoming "async" argument; otherwise it passes "false".

5. The ACR code performs the following steps:
    a) it creates a new Ctx object;
    b) it creates nFuture objects representing return values, each holding a CompletableFuture;
    c) it creates a Call Request, which is a Runnable object that represents an actual call to the
       SC and adds it to the service execution queue;
    d) if async flag is set to true, it immediately returns, passing the default value on the Java
       stack and the corresponding future in the Ctx;
    e) otherwise it blocks the execution, waiting for the callee to complete the CompletableFuture
       normally or abnormally, at which point it either returns the results following standard
       return conventions or throws;
    d) all passed in arguments need to be either immutable objects, proxies or services; the same is
       true for the return values; otherwise they have to be declared as interface classes, in which
       case an automatic proxy implementing that interface should be created.

6. All Future annotated variables and properties are implemented via the nFuture object. The
   implementation is simplified due to the fact that the Future annotation cannot be combined with
   any other Var annotation.
