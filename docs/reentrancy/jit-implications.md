# JIT Runtime Implications

This note is documentation only. It does not propose changing the JIT code in
this branch.

The inspection here is based on the `org.xvm.javajit` package in the current
branch and the newer `origin/JIT` branch. The broad conclusion is that the JIT
is not a thin execution mode on top of the interpreter runtime. It is a separate
runtime path with its own container, context, type-system, classloader, generated
singleton, and generated static-cache model.

That means the interpreter fixes in this branch are necessary, but they do not
automatically prove the JIT path safe.

## Relationship To The Interpreter Runtime

The JIT package does not use the interpreter runtime classes that this branch is
primarily fixing:

- no `org.xvm.runtime.Container`,
- no `Frame`,
- no `ClassTemplate`,
- no `ObjectHandle`,
- no `TypeComposition`,
- no `NativeTemplates`.

The JIT does use the shared `org.xvm.asm` model heavily:

- `ModuleStructure`,
- `ClassStructure`,
- `MethodStructure`,
- `ConstantPool`,
- `TypeConstant`,
- `TypeInfo`,
- `MethodInfo`,
- and other constant/metadata classes.

So the JIT has two separate implications:

- Interpreter native-template globals such as old `xBoolean.TRUE` or
  `xBit.ZERO` are not directly used by generated JIT bytecode.
- Any racy or owner-confused state in shared `asm` objects can still affect the
  JIT compiler and generated-code metadata because the JIT builds from those
  same structures.

## JIT Ownership Model

The JIT has its own runtime root: `org.xvm.javajit.Xvm`.

`Xvm` owns:

- the native JIT type system,
- the hidden native container,
- the Ecstasy and native bridge module loaders,
- weak maps of JIT containers, type systems, and module loaders,
- package/name caches used to assign generated Java class names,
- and the `AtomicLong` container id counter.

`org.xvm.javajit.Container` is a small immutable owner record:

- `xvm`,
- `parent`,
- `typeSystem`,
- `injector`,
- `id`.

It implements `LinkerContext`, but it is not the interpreter `Container` and it
does not have interpreter template/composition caches.

`org.xvm.javajit.Ctx` is the runtime execution context for generated bytecode.
Generated methods receive or obtain a `Ctx`, and `Ctx` carries:

- the JIT `Xvm`,
- the JIT `Container`,
- multi-return scratch slots,
- injection access,
- constant lookup by generated class name and pool index,
- and placeholder memory-accounting APIs.

`Ctx.Current` is a `ScopedValue<Ctx>`. JIT entry currently runs generated code
under:

```java
ScopedValue.where(Ctx.Current, new Ctx(xvm, container)).run(...)
```

Generated class initialization also uses `Ctx.get()` to initialize synthetic
constant fields. That makes the active `Ctx` part of generated class loading and
initialization semantics.

## ClassLoader And Cache Model

The JIT uses Java classloaders as ownership and cache boundaries:

- `TypeSystemLoader` represents a linked group of modules.
- `ModuleLoader` owns generated Java classes for one module/package prefix.
- `TypeSystem` can share module loaders from other type systems.
- `NativeTypeSystem` can load bridge classes and augment them with Ecstasy
  methods.

This is architecturally different from the interpreter:

- Interpreter: a `Container` owns native templates, compositions, handles, and
  runtime metadata.
- JIT: a `TypeSystem` / `ModuleLoader` owns generated Java classes and their
  static fields; a `Ctx` points each invocation at a JIT `Container`.

The intended performance model is also different. The JIT deliberately uses JVM
class initialization, classloader identity, static fields, and generated
bytecode to make hot paths cheap. That is reasonable, but only if generated
statics never capture state whose true owner is a different JIT container.

## Generated Static Fields

The generated bytecode uses Java static fields for at least two important
purposes:

- `$scN` synthetic constant fields for `TypeConstant` and other constants used
  by generated code,
- `$INSTANCE` singleton fields for Ecstasy singletons.

Static initialization is handled by generated `<clinit>` code. In
`CommonBuilder.assembleCLInit`, generated code obtains the current `Ctx`, uses
the generated class name and a constant-pool index, and calls:

```java
ctx.getConstant(className, index)
```

That can be safe if the static field belongs to the generated classloader/type
system and the resolved constant is also owned by that type system's module
loader. It is risky if class initialization is triggered under the wrong
`Ctx`, or if a static field caches a value whose true owner should be a specific
container rather than a shared module loader.

The singleton model is especially important. The JIT comments describe using
the normal Java singleton pattern via class initialization: a generated
singleton is created once for the generated Java class and then read from a
static `$INSTANCE` field. That gives good JVM memory-model publication, but the
owner is the classloader, not necessarily the calling container.

That is fine only for singletons whose semantics are genuinely shared at that
classloader/type-system boundary. It is not fine for anything that depends on a
container injector, service context, resource set, mutable state, or runtime
configuration.

## Similar Risk Categories To Track Later

Do not fix these in this branch, but they should be tracked as JIT-specific
ownership risks:

| Area | Risk | Proper direction |
| --- | --- | --- |
| Generated `$INSTANCE` fields | Classloader-wide singleton may be reused across containers that should not share state | Prove singleton ownership is type-system scoped, or route container-owned singletons through `Ctx.container` / a container-owned table |
| Generated `$scN` constant fields | Static constants are initialized from `Ctx`; wrong active `Ctx` can initialize a generated class with the wrong pool/module owner | Ensure generated class initialization is always under the owning type-system context; consider classloader/type-system owner checks in debug builds |
| Shared `ModuleLoader`s | Type systems intentionally share module loaders and generated classes for memory/performance | Document which module state is safe to share; keep container-specific state out of generated class statics |
| `Ctx.Current` | Generated class initialization and execution depend on a scoped current context | Fail fast if generated code or class initialization runs without a `Ctx`, and test parallel containers with different injectors |
| `NativeTypeSystem` caches | `nativeModels`, `nativeByClass`, and `nativeByType` are global to the native JIT type system and keyed by ASM constants/types | Keep these as type-system/native-loader caches only; never store container-owned runtime values there |
| `Xvm` weak maps | Containers, type systems, and module loaders are cached in concurrent weak maps | Keep creation/lookup atomic; review non-thread-safe mod counters as approximate cleanup only, not correctness state |
| `ModuleLoader.loadedClasses` | Plain `HashMap` of generated class bytes is mutated during class loading and debug dumping | Restrict to classloader lock/debug use or replace with a concurrent/snapshot map before parallel dumping |
| Debug/global JIT controls | `NativeNames.reservedMethodName`, `CommonBuilder.SKIP_SET`, `METHOD_SKIP_SET`, JIT lists, and connector dump lists are process-level debug/build controls | Make immutable where possible; keep mutable debug state out of correctness decisions |
| Shared ASM metadata | JIT relies on `TypeConstant`, `TypeInfo`, `MethodInfo`, and `ConstantPool` caches | Apply the same final/atomic/concurrent ownership audit to `asm`; interpreter fixes do not cover this automatically |

## What This Means For This Branch

The current branch's interpreter runtime changes are still correct and
necessary. They remove process-global native-template and handle caches from
the interpreter path.

The JIT path needs its own audit because it uses different owner boundaries:

- interpreter owner boundary: `Container` and its `NativeTemplates`,
- JIT compile/load owner boundary: `Xvm`, `TypeSystem`, `TypeSystemLoader`, and
  `ModuleLoader`,
- JIT execution owner boundary: `Ctx.container`.

For future JIT work, the rule should be:

- generated Java statics may cache type-system/classloader-owned immutable
  values,
- generated Java statics must not cache container-owned runtime values,
- generated code that needs container-owned state must reach it through
  `Ctx.container` or an explicitly owner-scoped table,
- and any shared `asm` cache used by both interpreter and JIT must be safe under
  parallel compilation/loading.

## Suggested Verification Later

The JIT should get a separate ownership dump similar to
`OwnershipDiagnostics`, but rooted at `org.xvm.javajit.Xvm`:

- list all live JIT containers and their ids,
- list type systems and shared/owned module loaders,
- list generated classes and their classloader owner,
- inspect generated `$INSTANCE` and `$scN` fields,
- flag generated statics whose value points at the wrong `Ctx.container`,
- and compare two parallel JIT containers with different injectors.

The key stress test should create two JIT containers in one `Xvm`, force both
to load the same shared modules, then execute code that touches:

- enum values,
- singletons,
- injected resources,
- constants loaded through `$scN`,
- arrays/views,
- and exceptions.

The expected result is that shared classloader/type-system state is identical
only where sharing is intentional, and every container-owned object is reached
through the active `Ctx.container`.

See [scoped-value.md](scoped-value.md) for the broader discussion of
`ScopedValue`, `Ctx.Current`, and whether a scoped runtime struct can safely
replace legacy ownerless static lookups.
