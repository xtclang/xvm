# ScopedValue And Runtime Ownership

This note evaluates the proposal to put legacy non-constant static runtime state
behind one thread-local or `ScopedValue`-held runtime struct. It is analysis
only; this branch does not implement that migration.

## Short Recommendation

`ScopedValue` is useful for ambient execution context. It can simplify some
legacy ownerless APIs by providing a single, explicit dynamic runtime scope.
It should not replace owner-scoped storage for native templates, handles,
compositions, type metadata, or other values whose real owner is a `Container`
or `ConstantPool`.

For the must-fix work in this branch, the safer model remains:

- store cached values in the owning object (`Container`, `NativeTemplates`,
  `ClassTemplate`, `ConstantPool`, or another explicit owner),
- keep those owner references in final fields where possible,
- use `Lazy`, `ConcurrentMap.computeIfAbsent`, `AtomicReference`, or explicit
  lifecycle state according to the cache semantics,
- require a `Frame`, `Container`, `ClassTemplate`, or `ConstantPool` at APIs
  that manufacture owner-bearing values,
- and fail fast when no owner is available.

A single `ScopedValue<RuntimeScope>` can be valuable as a transitional bridge
for old call sites that cannot yet accept an owner parameter, but it should
only point to the real owner-scoped tables. It should not become a new
container of mutable process-global caches.

## Terminology

This document uses two related but different terms.

### Ambient Execution Context

An ambient execution context is a value that is logically part of the current
call tree even when it is not present in every method signature.

In XVM terms, examples include:

- the active interpreter `Frame`,
- the active interpreter `Container`,
- the current `ServiceContext`,
- the current `ConstantPool` while resolving constants,
- or the JIT `Ctx` while generated bytecode is executing.

The context is "ambient" because deeply nested helper code can recover it
without every intermediate helper declaring and forwarding another parameter.
It is still bounded by a concrete operation: "run this method", "resolve this
constant", "serialize this structure", or "execute this generated JIT entry".

A small, sound example:

```java
final class RuntimeCall {
    private static final ScopedValue<Frame> CURRENT_FRAME = ScopedValue.newInstance();

    static int runWith(Frame frame, IntSupplier action) {
        return ScopedValue.where(CURRENT_FRAME, frame).call(action::getAsInt);
    }

    static Frame frame() {
        return CURRENT_FRAME.orElseThrow(() ->
                new IllegalStateException("No runtime frame is active"));
    }
}
```

Code inside the dynamic call can use `RuntimeCall.frame()` when it truly means
"the frame of the operation currently executing":

```java
int compare(ObjectHandle left, ObjectHandle right) {
    Frame frame = RuntimeCall.frame();
    return frame.assignValue(A_STACK, left.getTemplate().compare(frame, left, right));
}
```

That does not create or own cached state. It just transmits the current
execution owner through a call tree.

This is the kind of problem `ScopedValue` was chosen to solve in Java: lexical,
bounded, one-way context passing. It is preferred over a raw `ThreadLocal`
because the binding is restored automatically at scope exit, nested scopes are
explicit, and far-away callees cannot accidentally leave a new value behind
with `set()`.

### Transitional Owner Lookup

A transitional owner lookup is a compatibility shim for legacy static APIs that
were designed before owner correctness was explicit.

The old shape is unsafe:

```java
public static JavaLong makeHandle(boolean value) {
    return value ? ONE : ZERO; // ONE/ZERO are process-global handles
}
```

The final preferred shape is explicit:

```java
public static JavaLong makeHandle(Container container, boolean value) {
    return NativeTemplates.get(container).bit().makeHandle(value);
}
```

A temporary scoped bridge would keep the old signature only while migration is
in progress:

```java
@Deprecated
public static JavaLong makeHandle(boolean value) {
    return RuntimeScopes.current().templates().bit().makeHandle(value);
}
```

The scoped bridge is safer than the original static global because it selects
the current owner and fails if no owner is bound. It is still not as good as the
explicit API because the owner dependency is hidden from the method signature.

The crucial rule is that the bridge must not own the cache:

```java
public record RuntimeScope(Container container) {
    public NativeTemplates templates() {
        return container.nativeTemplates(); // real cache owner
    }
}
```

If `RuntimeScope` held its own mutable maps of templates or handles, it would
be another global-variable mechanism with a different access path. The
owner-local table must remain on the owner.

## What ScopedValue Is

`ScopedValue` is a Java 25 final API. The JDK describes it as a way to pass data
to methods without plumbing it through every intermediate method parameter. A
binding is active only for the bounded dynamic execution of a `run` or `call`
operation, and the previous binding is restored when that operation returns or
throws.

The important properties for XVM are:

- A `ScopedValue` binding is per thread.
- Nested scopes may rebind the same key, and the older value is restored at
  scope exit.
- Structured child tasks can inherit scoped values.
- The value bound into the scope must itself be immutable, confined, or
  correctly synchronized if multiple threads can observe it.
- The JDK expects programs to use a small number of scoped values; when several
  values need to travel together, the recommended shape is one record-like
  context object.

References:

- [JEP 506: Scoped Values](https://openjdk.org/jeps/506)
- [JDK 25 `ScopedValue` API](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/ScopedValue.html)

## Current Uses In This Code Base

Current `ScopedValue` uses are ambient-context mechanisms, not owner-cache
storage.

### JIT `Ctx.Current`

`org.xvm.javajit.Ctx` declares:

```java
public static final ScopedValue<Ctx> Current = ScopedValue.newInstance();
```

`org.xvm.javajit.JitConnector.invoke0` binds it around a generated-code
invocation:

```java
ScopedValue.where(Ctx.Current, new Ctx(xvm, container)).run(...);
```

Generated JIT code can then call `Ctx.get()` to recover the active `Xvm`,
JIT `Container`, injector, constant lookup helper, and multi-return scratch
slots.

This is a reasonable use: generated bytecode has a hot call boundary where
passing every execution-context value explicitly would be noisy, and the
context is tied to one dynamic invocation. It does not prove that generated
static `$INSTANCE` or `$scN` fields are safe; those fields are still classloader
state and need their own ownership rules, as described in
[jit-implications.md](jit-implications.md).

Why `ScopedValue` fits better here than the obvious alternatives:

- Passing `Ctx` explicitly everywhere would be safest and is still used for many
  generated method calls, but generated bytecode also needs context during
  helper calls and class initialization paths where adding another parameter to
  every edge is noisy and brittle.
- A mutable static `Ctx` would be wrong because two containers or fibers could
  overwrite each other.
- A plain `ThreadLocal<Ctx>` would work only with perfect `try/finally`
  cleanup. The scoped binding gives the desired dynamic lifetime directly.
- A container-owned cache alone is not enough for this case because `Ctx` is not
  just cached state; it is the current invocation's execution state.

### `TypeConstant.s_context`

`TypeConstant` uses a private static `ScopedValue<TypeConstant>` for temporary
type-relation context. It binds a context only while calculating specific
`isA`/relation probes, and `getContext()` treats an absent binding as no
context.

This is also a good use: the value is a temporary recursion/calculation
parameter. It is not a long-lived cache and it does not manufacture
container-owned runtime handles.

Here the alternatives are similar:

- Passing a context parameter through every `isA` and relation helper would be
  explicit, but it would force a broad signature change through very old,
  recursive type logic.
- A raw `ThreadLocal` would need manual cleanup on every exceptional path.
- A static mutable field would corrupt parallel type checks.
- A `ScopedValue` expresses the real lifetime: this relation calculation and
  its recursive callees.

### Older Thread-Local Contexts

The tree still has older thread-local patterns:

- `ConstantPool.s_tloPool` is the ambient current pool.
- `ServiceContext.s_tloContext` is the service context served by the current
  thread.
- `MultiMethodStructure.s_tloIgnoreNative` is a serialization flag.
- `TransientThreadLocal` supports per-instance short-lived recursion/deferred
  state.
- `xRTServer` keeps a per-thread request key-store handle.

Several of these could become `ScopedValue` later if their lifetime is truly
lexical. Others are better expressed as explicit parameters or owner-local
state. The important distinction is whether the state is a temporary dynamic
input to a computation or a stable cache with an owner.

For example, `ConstantPool.withPool(pool)` already has lexical intent:

```java
try (var ignore = ConstantPool.withPool(pool)) {
    // resolve constants against pool
}
```

That resembles a scoped value, but today it mutates a one-element array stored
in a `ThreadLocal`. A future `ScopedValue<ConstantPool>` could make the
lifetime structurally visible and remove the need for mutable holder arrays.
That would still be an ambient lookup for the current calculation, not a place
to store constants.

## Cameron's Proposal

Cameron's suggestion, restated: put the static non-constant runtime state into a
single thread-local or `ScopedValue`-held struct, so legacy static accessors can
resolve through the current runtime context instead of reading mutable static
fields directly.

A narrow version could look like this:

```java
public record RuntimeScope(Container container) {
    public NativeTemplates templates() {
        return container.nativeTemplates();
    }

    public ConstantPool pool() {
        return container.getConstantPool();
    }
}

public final class RuntimeScopes {
    private static final ScopedValue<RuntimeScope> CURRENT = ScopedValue.newInstance();

    public static RuntimeScope current() {
        return CURRENT.orElseThrow(() ->
                new IllegalStateException("No XVM runtime scope is bound"));
    }

    public static void run(Container container, Runnable action) {
        ScopedValue.where(CURRENT, new RuntimeScope(container)).run(action);
    }
}
```

Legacy static factories could then be reduced to one escape hatch:

```java
public static JavaLong makeHandle(boolean value) {
    return RuntimeScopes.current().templates().bit().makeHandle(value);
}
```

That shape is much better than hundreds of public mutable `INSTANCE` fields,
because:

- the static key is final and immutable,
- the binding has a bounded lifetime,
- missing scope fails immediately,
- call sites point through one owner API,
- and the actual caches still live under the owning `Container`.

It is not as strong as passing the owner explicitly, because the dependency is
still hidden and can fail only at runtime when code runs outside a bound scope.

## Interpreter Runtime Scope Sketch

This section sketches a possible non-JIT interpreter implementation. It is not
implemented in this branch. The goal would be to make owner lookup and
diagnostics feel like one familiar runtime facility instead of a pile of ad hoc
`frame.f_context.f_container`, `frame.container()`, and static helper rewrites.

The Java API name is `ScopedValue`, not `ScopeValue`; the important property is
that the binding is lexical and automatically removed at scope exit.

### API Shape

The interpreter could expose one small runtime scope API:

```java
public final class RuntimeScopes {
    private static final ScopedValue<RuntimeScope> CURRENT = ScopedValue.newInstance();

    private RuntimeScopes() {
    }

    public static RuntimeScope current() {
        return CURRENT.orElseThrow(() ->
                new IllegalStateException("No XVM runtime scope is bound"));
    }

    public static Container container() {
        return current().container();
    }

    public static NativeTemplates nativeTemplates() {
        return current().nativeTemplates();
    }

    public static <T> T call(Container container, Callable<T> action) throws Exception {
        return ScopedValue.where(CURRENT, RuntimeScope.forContainer(container))
                .call(action);
    }

    public static void run(Container container, Runnable action) {
        ScopedValue.where(CURRENT, RuntimeScope.forContainer(container))
                .run(action);
    }

    public static void run(Frame frame, Runnable action) {
        ScopedValue.where(CURRENT, RuntimeScope.forFrame(frame))
                .run(action);
    }

    public static <T> T call(Frame frame, Callable<T> action) throws Exception {
        return ScopedValue.where(CURRENT, RuntimeScope.forFrame(frame))
                .call(action);
    }
}

public record RuntimeScope(Container container,
                           ServiceContext service,
                           Frame frame) {
    public RuntimeScope {
        Objects.requireNonNull(container, "container");
        if (service != null && service.f_container != container) {
            throw new IllegalArgumentException("service belongs to a different container");
        }
        if (frame != null && frame.container() != container) {
            throw new IllegalArgumentException("frame belongs to a different container");
        }
    }

    public static RuntimeScope forContainer(Container container) {
        return new RuntimeScope(container, null, null);
    }

    public static RuntimeScope forFrame(Frame frame) {
        ServiceContext service = frame.f_context;
        return new RuntimeScope(frame.container(), service, frame);
    }

    public ConstantPool pool() {
        return container.getConstantPool();
    }

    public NativeTemplates nativeTemplates() {
        return container.nativeTemplates();
    }
}
```

That is intentionally a context accessor, not a cache owner. The `RuntimeScope`
record should contain final references to the active interpreter owner and
delegate every stable lookup to owner-local state such as
`container.nativeTemplates()`.

### Binding Points

Binding only around `InterpreterConnector.invoke0(...)` would not be enough.
`ScopedValue` is per-thread. The interpreter schedules service work onto
runtime-managed threads, and a binding on the launcher thread does not magically
cover work later executed by a different worker.

The scope would need to be bound at every interpreter entry where owner-bearing
runtime values can be manufactured or cached:

- `InterpreterConnector.start(...)` and `invoke0(...)` can bind while preparing
  the top-level call.
- `Container.schedule(...)` or `ServiceContext.execute(...)` must bind while a
  service is executing on a runtime worker thread.
- IO/native callbacks that re-enter the runtime must bind the owning
  `Container` or `ServiceContext` before calling back into handle/template
  helpers.
- Any diagnostic or stress-test launcher that runs containers in the same JVM
  can bind the scope around the executed runtime step, then still validate the
  completed container graph explicitly after the step returns.

A service wrapper would look like this:

```java
f_runtime.submitService(() -> RuntimeScopes.run(service.f_container, () -> {
    try {
        service.execute(true);
    } finally {
        f_pendingWorkCount.decrementAndGet();
    }
}));
```

If the scope carries a `Frame`, the binding should be refreshed at frame
dispatch boundaries, not stored in mutable static state:

```java
int dispatch(Frame frame) throws Exception {
    return RuntimeScopes.call(frame, () -> frame.nextOp().process(frame, frame.f_ahVar));
}
```

The exact method names would need to match the interpreter execution loop, but
the invariant is simple: every runtime worker that can create owner-bearing
objects enters through one lexical owner scope.

### Simplifying The Ownership Checker

The current `OwnershipDiagnostics` is deliberately an offline graph validator.
It starts from one or more completed `Container` roots, walks known owner-local
caches, and reports:

- owner-bearing objects stored below the wrong owner,
- constants held under a container with the wrong `ConstantPool`,
- and identities shared across containers where sharing is not allowed.

A `ScopedValue` cannot replace that offline check. After a run completes there
may be no dynamic scope active, and the point of the diagnostic is to compare
multiple container graphs at the same time. That still requires explicit
container roots:

```java
OwnershipDiagnostics.assertValid(containerA, containerB);
```

What a scoped runtime owner can simplify is online validation at creation and
cache-insertion points. The ownership logic currently buried inside the dumper
could be factored into a reusable helper:

```java
public final class RuntimeOwners {
    public static Container ownerOf(Object value) {
        if (value instanceof ClassTemplate template) {
            return template.f_container;
        }
        if (value instanceof TypeComposition composition) {
            return composition.getContainer();
        }
        if (value instanceof ObjectHandle handle) {
            TypeComposition composition = handle.getComposition();
            return composition == null ? null : composition.getContainer();
        }
        if (value instanceof ServiceContext service) {
            return service.f_container;
        }
        if (value instanceof NativeTemplates templates) {
            return templates.container();
        }
        return null;
    }
}
```

Then the scope can provide one assertion point:

```java
public record RuntimeScope(Container container,
                           ServiceContext service,
                           Frame frame) {
    public <T> T requireOwner(String label, T value) {
        Container actual = RuntimeOwners.ownerOf(value);
        if (actual != null && actual != container && actual != container.getNativeContainer()) {
            throw new IllegalStateException(label
                    + " returned " + value.getClass().getName()
                    + " owned by a different container");
        }
        return value;
    }
}
```

New or migrated helpers could use that without accepting another diagnostic
parameter:

```java
ObjectHandle hForm = RuntimeScopes.current().requireOwner(
        "xEnum.makeFormHandle",
        makeFormHandle(frame, type));
```

Owner-local caches could validate values as they are inserted:

```java
ClassTemplate template = f_mapTemplatesByType.computeIfAbsent(type, key ->
        RuntimeScopes.current().requireOwner("templatesByType", createTemplate(key)));
```

That gives earlier failures than a post-run dump. It also makes the rule easy
for contributors: if code is running under the interpreter and creates a
runtime handle, template, composition, or service, it can assert against the
current runtime scope. The deep graph dump remains the regression test and
failure artifact for "what escaped where?" after the fact.

### Simplifying Transitional Owner Lookup

The branch has intentionally removed many ownerless static accessors instead of
adding another ambient lookup. That is the stronger final shape. A scoped bridge
would still be useful where changing every call site in one PR is too wide.

For example, a migrated native helper should prefer the explicit form:

```java
public static BooleanHandle trueHandle(Container container) {
    return xBoolean.trueHandle(container);
}
```

A legacy bridge could exist temporarily:

```java
@Deprecated
public static BooleanHandle trueHandle() {
    return xBoolean.trueHandle(RuntimeScopes.container());
}
```

That bridge is much safer than `xBoolean.TRUE` because it cannot return a
process-global handle. It either resolves through the current owner or throws
because no runtime owner is bound. It is still weaker than the explicit API
because a method signature no longer reveals that the call depends on a
container.

This approach could reduce noisy plumbing in code that is purely interpreter
execution code:

```java
// Preferred when a frame is naturally available.
return xBoolean.makeHandle(frame.container(), value);

// Acceptable transitional bridge in old deep helpers that execute only
// under a bound runtime scope.
return xBoolean.makeHandle(value);
```

The bridge should be deprecated from day one and should delegate to the same
owner-local `NativeTemplates` table as the explicit API. It must not allocate
or cache anything inside `RuntimeScope`.

### What This Would Simplify In This Branch

A scoped interpreter owner could simplify some of the work this branch had to
do, but it would not make the owner-local tables unnecessary.

It could simplify:

- old helper methods that currently had to grow a `Container`, `Frame`, or
  `ClassTemplate` parameter only to recover the current owner,
- repeated `frame.f_context.f_container` or `frame.container()` plumbing in
  deeply nested interpreter-only helper paths,
- fail-fast checks that reject null owner arguments such as unsafe
  `makeInternalHandle(null, ...)` calls,
- owner assertions at template/handle/composition cache insertion points,
- and contributor ergonomics by matching the existing JIT `Ctx.Current` mental
  model.

It would not simplify:

- values created during linking, loading, or constant-pool work where there may
  be no active interpreter frame,
- values that must remain valid after the dynamic invocation returns,
- caches whose identity is semantically per `Container` or per `ConstantPool`,
- cross-container validation after a same-JVM stress run,
- constructor escape or unsafe publication,
- or any mutable shared state that still lacks synchronization.

The important distinction is whether the state is "current execution context"
or "owned cached state". `ScopedValue` is appropriate for the former. The
latter still belongs in final owner fields, `Lazy`, owner maps, or pool intern
tables.

### Soundness Conditions

This sketch would be sound only if all of these rules hold:

- `RuntimeScopes.CURRENT` is the only scoped key for interpreter ownership.
- `RuntimeScope` is an immutable record of owner references, not a bag of
  mutable caches.
- Every runtime worker entry that may allocate owner-bearing objects binds a
  scope before doing so.
- Owner-bearing factories still prefer explicit owner parameters when the owner
  is already available.
- Legacy ownerless bridges fail immediately when no scope is bound.
- Cache storage remains under `Container`, `NativeTemplates`, `ConstantPool`,
  `ClassTemplate`, or another real owner.
- Online scoped assertions and offline `OwnershipDiagnostics.assertValid(...)`
  share the same `ownerOf(...)` rules so they cannot diverge silently.
- Native-parent sharing remains a documented exception, not a blanket "any
  native object is fine" rule.

With those rules, the Java Memory Model story stays the same as in the current
branch: final fields publish the owner references, `Lazy` and concurrent maps
publish cached values safely, and the scoped value only chooses the owner for
the current call tree.

### Migration Plan

A later PR could introduce this without changing semantics:

1. Factor `OwnershipDiagnostics.ownerOf(...)` into a small package-private or
   public diagnostic helper such as `RuntimeOwners`.
2. Add `RuntimeScopes` and `RuntimeScope` with no runtime behavior changes.
3. Bind `RuntimeScopes` at interpreter service/frame entry points.
4. Add tests that ownerless bridge calls throw outside a scope and resolve to
   the correct owner inside two different container scopes.
5. Add online assertions at the highest-risk cache insertion points.
6. Convert only the noisiest legacy ownerless helpers to deprecated scoped
   bridges.
7. Keep the explicit owner APIs and remove bridges as call sites are migrated.
8. Keep the same-JVM sequence/parallel stress tasks running
   `OwnershipDiagnostics.assertValid(...)` against completed containers.

That would make the transitional runtime model feel familiar to contributors:
"inside interpreter execution, `RuntimeScopes.current()` is the owner context;
for durable cached state, use the owner table." It would not hide the preferred
end state, which is still explicit, final, owner-local state wherever practical.

## Why These Mechanisms Were Chosen Over Alternatives

The correct mechanism depends on what the state means.

| State shape | Preferred mechanism | Why |
| --- | --- | --- |
| Stable cached value owned by one `Container` | Final owner field plus `Lazy` or `ConcurrentMap.computeIfAbsent` | The cache key is the owner; publication is safe; repeated lookups are cheap |
| Stable cached value owned by one `ConstantPool` | Store it in that pool or compute through that pool's intern table | Constants are already interned per pool; a JVM-global cache can return a foreign-pool value |
| Current execution/frame/service/context | Explicit parameter first; `ScopedValue` when the parameter would be pure plumbing through many layers | The value is dynamic and lexical, not globally owned |
| Temporary recursion guard or calculation flag | `ScopedValue` or `TransientThreadLocal` with strict lexical use | The value is scoped to a calculation and must be restored on all exits |
| Legacy ownerless static helper | Temporary `ScopedValue<RuntimeScope>` bridge, then migrate to explicit owner parameter | Keeps compatibility while routing to the owner table |
| Shared process resource such as a terminal | Explicit process/runtime lifecycle owner with synchronization | It is intentionally process-level, but still mutable and must not masquerade as container metadata |
| Global table keyed by `Container` | Usually avoid; use `container.nativeTemplates()` or another owner-owned table | External global maps create lifetime/leak questions and keep ownership hidden |
| Public mutable `INSTANCE` field | Never for owner-bearing runtime objects | It races, breaks final publication, and can return foreign-owner values |

The branch uses `NativeTemplates` and explicit owner parameters for the
must-fix native-template cases because they are stable caches, not dynamic
execution context. A scoped bridge could reduce churn during a larger migration,
but it would be weaker evidence than the current method signatures.

The JIT uses `Ctx.Current` because generated code has a different problem:
there is a current invocation context that must be visible to generated helpers.
That context should point to owner-local state; it should not itself become the
owner of classloader-wide or container-wide caches.

## Will It Work For The Must-Fix Bugs?

It can work as a compatibility layer. It is not the best final fix for the
bugs this branch is removing.

The must-fix bugs are owner bugs, not only lookup bugs. The broken pattern was:

1. A constructor or bootstrap method publishes a template or handle into a
   mutable static field.
2. Another container later reads that field.
3. The reader receives an object whose `ClassTemplate`, `TypeComposition`,
   `ObjectHandle`, or `ConstantPool` belongs to a different owner.

A `ScopedValue` can make step 2 choose the active owner instead of a global
field, but the cached object still has to be stored in the active owner. If the
scoped struct itself owns mutable maps of templates or handles, it simply
renames the global cache problem. If the scoped struct points to
`container.nativeTemplates()` and the value is cached there, it is sound.

For this branch, explicit owner parameters and `NativeTemplates` are therefore
better:

- they are statically visible in the method signature,
- they work even when a value is created outside an interpreter/JIT invocation
  scope,
- they avoid accidental capture of the wrong dynamic scope,
- they preserve cache identity per owner,
- and they let tests prove that two containers receive distinct owner-bearing
  objects.

## Where ScopedValue Could Help Later

`ScopedValue` is worth considering for:

- replacing `ConstantPool.s_tloPool` if all callers can be moved from
  `setCurrentPool()` mutation to lexical `withPool(...)` scopes,
- replacing `MultiMethodStructure.s_tloIgnoreNative` with a lexical
  serialization scope,
- replacing `ServiceContext.s_tloContext` if service execution has a bounded
  scope that covers all code that needs the current service,
- request-local values in server code, such as the current key-store handle,
- a single `RuntimeScope` bridge for legacy ownerless runtime APIs during a
  staged migration,
- and diagnostics that assert every owner-bearing allocation happens under
  either an explicit owner parameter or a bound runtime scope.

It is not the right primary tool for:

- native template instance caches,
- value handles such as Boolean/Nullable/Ordered/Bit singletons,
- `TypeComposition` caches,
- constant-pool-owned metadata,
- service-owned mutable state,
- or any value that is expected to be reusable after the dynamic scope exits.

Those belong in explicit owner tables.

## Pros And Cons Of A RuntimeScope Bridge

Pros:

- It centralizes legacy ownerless access behind one API instead of hundreds of
  mutable statics.
- It is safer than `ThreadLocal` because scope exit is automatic.
- It works naturally with JIT-style generated code that already expects an
  ambient `Ctx`.
- It can be introduced incrementally: old static accessors can delegate through
  the current scope while new code takes explicit owners.
- It gives a clear debug assertion point for "this code needs a runtime owner".

Cons:

- It still hides dependencies from method signatures.
- It is per dynamic execution, not per object; escaped objects still need real
  owner fields.
- It can break code that legitimately builds metadata outside a bound runtime
  invocation unless those paths are given explicit owners.
- It needs careful propagation across any unstructured thread handoff. Structured
  child tasks inherit scoped values, but ordinary executor submission does not
  automatically make the lifetime correct.
- If the bound struct is mutable and shared across threads, the struct's fields
  still need normal synchronization or immutable/final publication.
- It can mask missing owner plumbing if kept forever instead of used as a
  migration aid.

The practical rule: use one scoped `RuntimeScope` only as a bridge to explicit
owner state, not as another cache owner.

## Why ScopedValue Does Not Fix Constructor Escape

The `this`-escape issue is separate. A constructor escape happens when an object
is made visible before construction has completed, often by calling an
overridable method, registering `this`, or publishing `this` into a static or
owner table.

The current JDK `javac` lint documents `this-escape` as a warning for
constructors that may leak `this` before subclass initialization. The warning
is available as `-Xlint:this-escape`; modern builds can turn it into a hard
error with `-Werror`. The rule should be treated that way for new XVM runtime
code, with any intentional exception carrying:

```java
@SuppressWarnings("this-escape") // explanation of why this object is safe here
```

Reference:

- [JDK 25 `javac` lint documentation](https://docs.oracle.com/en/java/javase/25/docs/specs/man/javac.html)

`ScopedValue` does not make constructor escape safe. If a half-initialized
object is published through a scoped binding, a static table, a callback, or an
owner cache, the object has still escaped. The correct fix is to separate
construction from publication:

- initialize all final fields in the constructor,
- do not call overridable methods from constructors,
- do not register `this` from constructors unless the class is final/private
  enough and the target cannot call back,
- publish fully initialized objects through owner-scoped APIs,
- and use explicit post-construction initialization only when the lifecycle is
  documented and guarded.

## Suggested Direction

For this branch:

- keep the current `NativeTemplates`/`Lazy`/explicit-owner fixes,
- do not replace them with `ScopedValue`,
- do not add JIT changes,
- and keep removing ownerless static factories one class at a time.

For a later compatibility wave:

1. Add one runtime-owned `RuntimeScope` API, probably bound at interpreter
   container/service entry and JIT `Ctx` entry.
2. Make ownerless legacy helpers delegate through that API only where passing an
   explicit owner is too invasive.
3. Keep all actual cached templates, handles, constants, and compositions in
   owner-local final state or concurrent maps.
4. Add diagnostics that fail when owner-bearing values are allocated or returned
   outside an explicit or scoped owner.
5. Enable `-Xlint:this-escape` for new/changed runtime code first, then move
   toward `-Werror` with documented suppressions.

That gives the short-term benefit Cameron is pointing at: a single place to
stop the worst legacy globals from choosing the wrong owner. It does not give
up the stronger long-term direction: reentrant code whose state ownership is
visible, final where possible, and testable per container.
