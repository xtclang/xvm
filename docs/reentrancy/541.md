# Issue #541: Permanent Injector Deadlock On Master (Analysis)

Analysis of https://github.com/xtclang/xvm/issues/541 (mrcompator / Michael
Raasch, 2026-08-24): intermittent permanent deadlock (0% CPU, never recovers)
in the shared per-container injector chain under heavy concurrent load,
reproduced on unmodified master, 5 out of ~8 runs of a 12-worker jsondb
stress test.

## Verdict up front

- **This is a genuine master bug, and it is NOT one this branch has tracked.**
  Our ledger's only deadlock rows are the singleton same-fiber recursion
  (fixed with `InitializingHandle`) and the ConstantPool registration-guard
  deadlock (branch-internal, our own guard). Nothing in the backlog covers
  fiber wait-graph cycles or the injection round-trip. This document adds it.
- **It is not fixable by a small hunk.** The root cause is a design gap
  (no cycle detection over the fiber wait graph) amplified by the injection
  architecture (every `@Inject` in a nested container is a fresh cross-service
  round-trip through default-synchronized services). It does not belong on
  the Category A quick-extraction list; it needs its own workstream.
- **The reported chain is internally consistent with the runtime code.** The
  mechanics check out end to end; details below with file:line references.
- **Plausibly the same root cause as the intermittent parallel-runner and
  jsondb-suite hangs we observed during stress work on this branch** (hangs
  that vanished on retry and were never root-caused). The issue itself was
  found while chasing a jsondb test-suite hang.

## Why the deadlock happens (runtime mechanics)

Four facts about the interpreter combine into the cycle Michael captured:

1. **Every `@Inject` in a nested container is a live cross-service call.**
   `NestedContainer.getInjectable(...)` (NestedContainer.java:133) resolves
   through an `InjectionSupplier` that invokes the container's
   `ResourceProvider` — for xunit containers, the Ecstasy `PassThruInjector`
   service. There is no per-container cache of resolved container-stable
   resources: `ObjectStore.updateReadStats()`'s `@Inject Clock` and
   `Catalog.log()`'s `@Inject Console` each round-trip through the provider
   service chain on every single call.

2. **A blocked fiber freezes its whole service unless the entire frame stack
   is concurrent-safe.** `Frame.getSynchronicity()` (Frame.java:1869-1879)
   returns `Concurrent` only when `isSafeStack()` holds for every frame on
   the stack; otherwise the fiber blocks in `Synchronized` mode, and
   `ServiceContext` will not interleave any other pending fiber until it
   resumes. `PassThruInjector.inject()` (xunit.x:48-64) is not `@Concurrent`,
   so while it awaits the downstream injector, the entire injector service is
   frozen — this is the "strictly FIFO" behavior in the report. The same
   applies to `SimpleInjector`/`TestInjector` and to the engine's
   `ExecutionContext` service while its fiber synchronously awaits the test
   method's completion.

3. **The runtime has no deadlock detection — by its own admission.**
   `Fiber.m_frameBlocker` (Fiber.java:715) is documented "Used for deadlock
   detection", but the only consumer in the entire runtime is
   `DebugConsole` (DebugConsole.java:1944-1947), which *displays* it.
   `Fiber.reportWaiting()` (Fiber.java:512) — itself debug-only — carries the
   literal comment `// TODO: check for the deadlock`. There is no code
   anywhere that walks the wait graph and breaks or reports a cycle. A
   genuine circular wait therefore hangs forever at 0% CPU, exactly as
   observed (`queued=0, awaiting=<poolSize>, active=0`).

4. **The xunit injector chain contains a back-edge into its own ancestry.**
   `TestInjector.contextLookup()` (TestInjector.x:88-95) calls
   `ctx.lookup(...)` — a service call back into the engine's
   `ExecutionContext`, which is owned by the same fiber lineage that
   originated the running test method. Resolution of *any* injection can
   therefore depend on the progress of the very code that is blocked waiting
   for an injection.

The captured cycle, in those terms:

```
test-method fiber            awaits  @Inject Clock          (fact 1: live round-trip)
  -> queued on PassThruInjector, frozen Synchronized        (fact 2)
       behind @Inject Console (Catalog.log), whose resolution
  -> TestInjector.contextLookup -> ctx.lookup               (fact 4: back-edge)
  -> ExecutionContext service frozen Synchronized while its
     fiber awaits the test method's completion              (fact 2)
  -> test method cannot complete: it awaits @Inject Clock   (cycle closed)
```

No participant is buggy in isolation; the FIFO freeze (2) plus the back-edge
(4) plus the per-call round-trip (1) create a classic circular wait, and (3)
guarantees it is permanent instead of detected.

## Why it is intermittent

The cycle needs an unlucky interleaving: a `Catalog.log()` Console request
must be *in flight* through the injector chain at the moment a worker's read
path submits its Clock request, while the engine context fiber is inside its
synchronized await. Twelve workers x 1500 transactions x one fresh injection
per read/log makes that window large enough to hit in most runs (5/8), but
it is still a race — which matches "intermittent, under sustained load".

## Relation to this branch's work

- **Not previously tracked** — added to the backlog as a new master-bug row
  referencing this document and the issue.
- **The diagnostic gap is exactly what the world X-ray plan covers.** Michael
  had to hand-build a fiber/service dependency dump to see the cycle. X-ray
  slice 2 (execution-state capture in `ownership-diagnostics.md`) specifies
  fiber -> pending-request -> target-service edges; this issue is the
  strongest possible justification for finishing that slice, and the natural
  acceptance test is: snapshot a hung run of Michael's reproducer and have
  the cycle print itself.
- **The injection-caching angle aligns with existing branch work.** The
  `InjectedHandle` hardening (first-wins CAS, ledger row for
  `xInject`) already treats an injected value as resolve-once; a
  per-container cache of container-stable resources (Clock, Console) is the
  same philosophy applied one level up, and would shrink both the deadlock
  window and the per-call overhead.
- **The runtime's own `// TODO: check for the deadlock` predates us** — the
  gap is acknowledged in master's source.

## Fix directions (options, not yet started)

1. **Wait-graph cycle detection (the real fix, runtime-level).** The runtime
   already has every edge it needs: `Fiber.m_oPendingRequests` (fiber -> the
   requests it awaits), each request's target `ServiceContext`, and each
   context's currently-blocking `Synchronized` fiber. The cheap trigger is
   the exact signature Michael measured: when the scheduler pool goes fully
   idle (`queued=0, active=0`) while fibers are still `Waiting`, walk the
   graph; on a cycle, complete one victim request exceptionally with a
   `Deadlock` exception naming the cycle. At 0% CPU the scan costs nothing,
   converts a permanent hang into a diagnosable failure, and needs no
   language change.
2. **Per-container caching of container-stable injections** (mitigation +
   performance): resolve Clock/Console-class resources once per container
   and serve subsequent `@Inject` occurrences locally. Shrinks the window;
   does not eliminate cycles for genuinely dynamic resources.
3. **Library-level hygiene in xunit** (mitigation, upstream code):
   `@Concurrent` on `PassThruInjector.inject()` (removes the FIFO freeze at
   the choke point) and avoiding the synchronous back-edge from
   `TestInjector.contextLookup` into the engine's own `ExecutionContext`.
   Fixes this instance, not the class.

Recommended order: (1) is the class fix and the only one that turns any
future cycle from a silent hang into an error; (2) and (3) are worthwhile
independently but must not be sold as the fix.
