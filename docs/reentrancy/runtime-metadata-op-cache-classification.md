# Runtime Metadata And Op Cache Classification

This audit covers the remaining runtime metadata caches and decoded `Op` link/address caches called
out by the reentrancy backlog, plus the follow-up scope around `ObjectHandle.cloneAs(...)`,
`GenericHandle.maskAs(...)`, `RefHandle` view backing, same-owner access views, and cross-owner guard
status.

Inputs read:

* `docs/reentrancy/must-audit-backlog.md`
* `docs/reentrancy/manual-lazy-cache-audit.md`
* `docs/reentrancy/state-inventory.md`
* `docs/reentrancy/runtime-ownership-hardening-ledger.md`
* `docs/reentrancy/fixed-in-this-branch.md`
* `docs/reentrancy/clone-usage-audit.md`

Status labels:

* `MUST FIX`: source inspection shows shared runtime state can be corrupted or owner-contaminated.
* `MUST AUDIT`: source shape is unsafe or unproven for shared/runtime publication, but the runtime
  reachability or invariant still needs a proof.
* `SHOULD FIX`: low-risk unsafe publication or mutability where failure is expected to be duplicate
  work or identity churn, but a small hardening change would remove the risk.
* `DONE`: this branch already contains the hardening or an adequate proof plus tests.
* `PROVEN CONFINED`: the state is compile-time, assembly-time, JIT-build-time, or otherwise not
  reachable from shared decoded runtime objects.

## Top Conclusions

1. `JumpVal` and `JumpVal_N` are fixed in this branch. The old runtime switch
   caches were removed from the shared decoded `Op` objects and replaced by
   `Container`-owned runtime-op cache entries keyed by `(decoded op, cache
   category)`. The cached tables still contain the same case-handle arrays,
   jump maps, wildcard/range masks, algorithm choices, and frame-derived
   `TypeConstant` data; the difference is that each executing container builds
   and reuses its own table instead of letting the first container in the JVM
   publish its owner state globally.
2. `JumpNFirst.m_fVisited` is fixed in this branch. The opcode is emitted for
   `assert:once`, and both `AssertStatement.isOnlyOnce()` and the opcode
   definition describe "first time execution reaches this op" semantics. The
   owner key therefore remains the decoded op, but the state is now a final
   `AtomicBoolean` so concurrent first execution has exactly one winner.
3. `JumpNSample.m_nEvery` is fixed in this branch. That field cached a runtime
   operand on the decoded op. `AssertStatement` validates the interval as a
   runtime constant, but the value still arrives through the current `Frame` as
   an `ObjectHandle`; storing the first handle value on the op would make later
   invocations use the first caller's sampling interval. The op now derives the
   clamped interval from the current handle on every execution.
4. Same-owner `GenericHandle` access-view backing is fixed in this branch. The old
   `GenericHandle.cloneAs(...)` shallow-cloned the handle, shared the final field array, and rewired
   inflated `RefHandle.OUTER` entries in that shared array (`ObjectHandle.java:62`,
   `ObjectHandle.java:497`, `ObjectHandle.java:503`, `ObjectHandle.java:512`,
   `ObjectHandle.java:649`). That meant creating one same-owner access view could mutate the source
   view. The replacement keeps the shared field array for regular values and adds sparse per-view
   overrides only for inflated refs whose `$outer` is view-specific.
5. Pure `Op` address/link fields are not owner-bearing runtime data, and this
   branch now closes the first-publication hazard for decoded code. `m_code` is
   a volatile publication cell and `ensureCode()` synchronizes first decode.
   Decoded code is linked during decode; compiler-owned code is linked by the
   normal `prepareOps()`/assembly path before it can be treated as runtime
   code. `getAssembledOps()` deliberately does not become a hidden linker.
   The diagnostics property `xvm.asm.validateRuntimeCode` verifies the linked
   state at `MethodStructure.getOps()`. The remaining follow-up is architectural:
   `MethodStructure.Code` is still a mutable compiler/assembly object, so a
   future `ResolvedCode` or freeze boundary would be cleaner than treating the
   whole lifecycle as immutable.

## Op Address/Link Decision

The address/link group is not currently a `MUST FIX` for owner contamination because the inspected
fields store op references, offsets, exit counts, and scope/finally metadata, not `Frame` constants
or owner-bearing handles. It is also not `DONE`: the source shows eager resolution, but not safe
publication.

To close this as `DONE`, one of these proofs is required:

1. Eager-publication proof: every runtime-reachable `MethodStructure.Code` is constructed,
   `addressAndSimulateOps()` has run, and the linked op array is safely published before any `Frame`
   can obtain `function.getOps()`.
2. Owner-state fix: `MethodStructure.ensureCode()` safely publishes one fully linked code snapshot,
   e.g. synchronized/volatile/atomic `m_code`, with `Code` fields final or otherwise safely
   published.
3. Runtime diagnostic proof: instrumentation counters on `addressAndSimulateOps()` and
   `Op.resolveAddresses()` prove they never run after method/container runtime publication, and
   parallel first-execution stress cannot observe unresolved link fields.

If none of those proofs is accepted, the proper classification should be promoted from `MUST AUDIT`
to `MUST FIX` for the code publication cell, not for every individual op field.

Current audit result: this branch applies the minimal first-publication fix and
diagnostic guard, not the full long-term `ResolvedCode` refactor.
`MethodStructure.m_code` is now a volatile owner cell, first construction is
synchronized, decoded code links during construction, and compiler-owned code
must still go through the existing preparation/assembly path. That prevents
parallel first runtime access from racing two decoded code objects or observing
constructor-written link state through a plain field without changing
`getAssembledOps()` into a hidden linker for mutable assembly code.

The remaining lifecycle concern is broader than the volatile cell:
`MethodStructure.Code` is also used as compiler/assembly state and is tied to
`m_abOps`, `m_registry`, `m_cVars`, `m_cScopes`, `createCode()`,
`resetRuntimeInfo()`, `setAbstract()`, `cloneBody()`, and reassembly paths. A
future cleanup should split mutable builder code from a frozen runtime
`ResolvedCode` snapshot. Until then, run runtime stress with
`-Dxvm.asm.validateRuntimeCode=true`; the diagnostics hook throws if a frame
receives code whose branch/switch/guard links are not ready.

## Same-Owner View Equivalence Proof

The cross-owner guard and same-owner view backing are both fixed and tested. The important invariant
is that `cloneAs(...)` is an access-view operation, not an object copy:

* Behavior: a source handle and each access-view clone share regular field storage; writes through
  either view are visible through the other.
* Behavior: inflated `RefHandle` values have per-view holder/backing state, so creating a struct view
  does not rewrite refs already visible through the revealed view, and vice versa.
* Behavior: refs obtained before masking/revealing continue to address the same logical property and
  do not silently switch holders when another view is created.
* Behavior: cross-owner masking still rejects non-shared handle graphs before `cloneAs(...)` is
  reached.
* Performance: the fix must not turn access masking into a deep copy of the full handle graph.
  Acceptable designs include a small shared backing object plus lazy per-view inflated-ref wrappers,
  or another representation with equivalent asymptotic behavior.
`GenericHandleCloneAsTest.sameOwnerCloneKeepsInflatedRefOuterViewLocal()` covers those semantics
directly using synthetic runtime handles. The test is intentionally written without branch-only
factory APIs so it can be copied onto master; on master it fails because the source ref's `$outer` is
rewritten to the clone. The fixed branch passes and also asserts that referent writes and regular
field writes still flow through the shared backing.

The chosen implementation is performance-equivalent to the old hot path:

* Handles with no access-view override still read and write the original final `m_aFields` array.
* Same-owner views still share regular field storage, so masking/revealing is not a deep copy of the
  full handle graph.
* Extra allocation is bounded by the number of inflated refs that actually need a different
  `$outer`, not by the total object graph size.
